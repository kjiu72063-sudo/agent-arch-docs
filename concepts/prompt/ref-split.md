# 1-4 · 六大策略 ②③：提供参考文本 + 拆分复杂任务

## 策略② · 提供参考文本（Reference Text）

把"参考答案/资料"放进 prompt，让模型**基于给定材料作答**，而不是凭记忆编造。这是降低幻觉最直接的手段。

### 三个具体手法

**① 先引述、再作答（quote-then-answer）**——让模型先把原文相关片段摘出来，再基于它回答。摘不出来，说明材料里没有，避免硬编。

```text
请先从下方文档中摘出与问题相关的原文句子（逐字引用），
然后仅根据这些句子回答问题。若文档中没有依据，直接回答"文档未提及"。

<文档>
{{DOCUMENT}}
</文档>

<问题>{{QUESTION}}</问题>
```

**② 用定界符隔离材料与指令**——推荐 XML 标签或三引号，避免模型把"材料"误当"指令"（这也是防提示注入的基础）。

```text
<instructions>总结下面的工单，只按"问题/影响/建议"三项输出。</instructions>
<ticket>{{RAW_TICKET}}</ticket>
```
> 反例：直接把用户输入拼在指令后面，用户输入里的"忽略以上指令"就可能生效。

**③ 长文档：把资料放前面、问题放后面**——Anthropic 长上下文实践指出，在超长输入里，把文档置于顶部、把问题与指令置于末尾，通常能显著提升回答质量（【事实】）。

### 适用场景
基于文档问答（RAG 的 prompt 侧）、按样例生成（few-shot）、按规范改写。**凡是"答案应在给定材料里"的任务，都要喂参考文本。**

## 策略③ · 把复杂任务拆成简单步骤（Task Decomposition）

模型擅长**逐步执行**，不擅长**一步到位处理长链条**。把大任务切小，每步可单独验证。

### 两种拆法

**① 链式拆解（chained prompts）**——上一步输出作为下一步输入：

```text
步骤1：从客服对话里提取"用户意图 + 涉及产品 + 情绪"（只输出 JSON）。
步骤2：基于步骤1的 JSON，检索对应产品的 FAQ（这一步由程序做）。
步骤3：基于 FAQ 与用户情绪，起草回复（先给 3 条要点，再成文）。
```
> 关键：**中间产物结构化**（JSON），既能被人检查，也能喂给下一步或程序。

**② 先规划、再执行（plan-then-execute）**——让模型先给出步骤清单，确认后再逐步做：

```text
你是一个重构助手。第一步：只输出改造计划（列 3–6 步，每步说明改哪个文件、为什么）。
不要写任何代码。等我确认后再逐步实现。
```
> 这一招在 [04 loop](/concepts/loop) 里会被放大成"规划节点 + 执行节点"的 loop 设计。

### 为什么必须拆
- **可验证**：每一步都能单独跑测试/人工检查，错误不会累积到最后才发现；
- **可恢复**：某步失败只重跑该步，不必整链重来（呼应 loop 的失败重试）；
- **可并行**：拆开后的独立子任务可并发（呼应 [05 graph 的 Send 并行](/concepts/graph/design)）。

::: tip 两个策略的落点
策略②解决"凭空编"（给依据），策略③解决"一步崩"（分步骤）。两者都服务于**可控、可验证**——这正是后面 harness / loop 反复强调的工程纪律。
:::

## 小测验

::: details 点击展开题目与答案
**Q1（选择）**：要减少"凭空编造"，最直接的做法是？  
A. 提高温度　B. 把参考资料放进 prompt 并要求先引述再作答　C. 让模型"务必准确"  
✅ B。给依据 + 要求引述，比口头强调有效。

**Q2（判断）**：长文档任务里，把问题放文档前面、资料堆在后面更好。  
❌ 错。长输入中资料放前、问题放末尾通常更好。

**Q3（选择）**：拆解任务的最大工程收益是？  
A. 让 prompt 更长　B. 每步可独立验证/恢复/并行　C. 可以少写代码  
✅ B。
:::
