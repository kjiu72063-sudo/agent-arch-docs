# 1-3 · 六大策略 ①：写清晰的指令

::: info 难度分层 · 本页 = L0→L1（prompt 基础层）
L0 看懂概念与类比；L1 能照本页示例手写出可用 prompt。读完 1-1 ~ 1-7 即达成 Track A 的 L1 基线。
:::


模型不理解"潜台词"，只理解你写的字。**越具体、越明确，发挥越稳定**——这是"把玄学变工程"的第一步。

## 清晰指令的五个要素

| 要素 | 要写什么 | 反例 → 正例 |
|---|---|---|
| 角色 | 它是谁、以什么视角做 | "帮我看看" → "你是资深代码审查者" |
| 任务 | 具体完成什么、范围边界 | "优化一下" → "把这段查询的耗时降低" |
| 输出格式 | JSON / 列表 / 几段 / 多长 | "给我结果" → "只输出 JSON，字段 name/price/url" |
| 条件与边界 | 必须做、禁止做、例外 | 无 → "不改函数签名；不加新依赖" |
| 成功标准 | 怎样算做对（可验证） | "写得好一点" → "npm test 全绿且无 lint 报错" |

> 模糊词是头号杀手：**"尽量好""适当优化""大概写写"**都要替换成可度量的说法。

## 烂 vs 好（对照）

> ✕ "给我写个 python 爬虫。"

> ✓ "写一个 Python 函数 `fetch_title(url)`，用 requests 抓取并返回网页 `<title>` 文本；请求超时设 5 秒，失败返回 None。**只输出完整可运行的函数，不要解释。**"

差别在于：✓ 版本给全了**函数名、返回值、依赖、超时、失败行为、输出要求**——每一项都是模型"本该猜"的东西。

## 三个实操技巧

**① 用角色设定锚定视角与语气**
```text
你是一名严格遵守 PEP8 的 Python 后端工程师，回答只给代码 + 必要的风险提示。
```

**② 用分隔标签把"指令"与"待处理内容"隔开**（防内容被误当指令）
```text
<任务>为下面的函数补类型注解</任务>
<代码>
def add(a, b):
    return a + b
</代码>
```
> 做法：用 XML 标签或三引号包裹"内容区"，让模型明确区分"我要你做的"和"你要处理的"。

**③ 一条提示只主攻一件事**，多任务拆开（见 [1-4 策略③](/concepts/prompt/ref-split)）。把"改代码 + 写测试 + 更新文档"塞进一条，出错时你无法定位是哪一步崩的。

## 什么时候还需要 few-shot

指令写不清"想要什么风格"时，**给 1–3 个输入→输出样例**比继续描述更有效：

```text
把用户反馈分类为 正面/负面/中性。示例：
输入：这个功能太好用了  → 输出：正面
输入：等半天没反应    → 输出：负面
输入：今天下雨了      → 输出：中性
输入：{{NEW_FEEDBACK}} → 输出：
```
> 样例是"隐式规范"：模型从样例里学到的是你**没写出来**的那些边界规则。

## 小测验

::: details 点击展开题目与答案
**Q1（选择）**：下列哪条最"清晰"？  
A. 帮我优化下代码　B. 把 `query_user` 的 N+1 查询改掉，返回同样的数据结构，附改动说明　C. 好好写  
✅ B。

**Q2（判断）**：指令和待处理的用户内容可以混在一起写，模型分得清。  
❌ 错。应使用分隔标签隔离，既提升稳定性，也防提示注入。

**Q3（选择）**：什么时候用 few-shot 最划算？  
A. 永远都用　B. 当"风格/边界"难以用语言描述清楚时　C. 提示词越长越好  
✅ B。
:::

清晰指令是"常驻说明书"（system prompt）的基础，也是 prompt 这一层最该先练好的技能。
