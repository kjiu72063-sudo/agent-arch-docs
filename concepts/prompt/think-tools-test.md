# 1-5 · 策略④ 让模型思考 · ⑤ 使用外部工具 · ⑥ 系统测试

这三条开始把"写提示词"升级为"搭系统"：推理、工具、验证。

## 策略④ · 给模型时间"思考"

> ✕ "直接告诉我：3.9 和 3.11 谁大？" —— 常被"急着答"带偏。

> ✓ "请先列出推理步骤，再给出结论。" —— 先想后答，正确率更高。

::: tip 落点
这就是 `loop` 里"先推理再动手"的雏形。
:::

## 策略⑤ · 使用外部工具

模型自己不会算、不会查、不会执行代码，但它能**请求调用工具**，拿到结果再继续。这就是工具调用（tool use）。

::: tip 最小样例 · 工具 + 验证
任务："读 package.json，找出 scripts.test，只读不改"。
① 模型请求 `read_file("package.json")` → ② harness 执行并回灌内容 → ③ 模型提取 `scripts.test`。
**怎么验证做对了**：把结果 `JSON.parse`，断言 `json.scripts.test` 非空——让"检查"交给程序，而不是靠人眼。
:::

## 策略⑥ · 系统地测试改动

- **攒一组固定问题（评估集）**：每次改 prompt 都跑一遍。
- **看回归**：改好了 A，别弄坏了 B。
- **量化**：用"通过率"而不是"感觉更好了"。

最小评估集（示意）：

```
case-01  总结公司年假政策        → 期望：5 条要点，且不含原文外内容
case-02  读取 package.json 找 test → 期望：返回 scripts.test
case-03  把 for 改成 map          → 期望：行为不变 + 注释
-------- 每次改 prompt 都整组重跑；通过率 = 通过数 / 总数
```

::: tip 落点
"用验证守护不变量"正是 `harness engineering` 的"机械化执行"思想。
:::
