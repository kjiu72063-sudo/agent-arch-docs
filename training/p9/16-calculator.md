## (3) 参数与公式的对应（拧哪一个 → 动哪一项）

| 控件 | 影响的账本项 | 公式 |
|---|---|---|
| `总参数量` | 权重 | `Φ × 位宽字节` |
| `混合专家 (MoE)` | 权重（**全部加载**） | MoE 的总参必须全量驻留（[9-3](/training/p9/03-weights-params)） |
| **`注意力机制结构`** | **KV Cache（改公式形态）** | MHA/GQA/MQA/SWA 用通式；MLA/DSA 用潜变量式；CSA2 再 `÷ 4` |
| `KV 头数` | KV Cache | `n_kv` 因子（GQA/MQA 的旋钮） |
| `KV 潜变量 d_c` | KV Cache（仅 MLA 系） | `d_c` 因子 |
| `滑动窗口 W` | KV Cache（仅 SWA） | 有效长度 `min(s, W)` |
| `序列长度` | KV + 激活 | 线性 |
| `批量大小` × `并发用户数` | KV + 激活 | `b × C` 两个乘数 |
| `推理量化` | 权重 | `FP16 2B / FP8·INT8 1B / INT4 0.5B` |
| `KV 缓存量化` | KV Cache | `2B / 1B / 0.5B` |
| `分块预填充` + `预填充分块大小` | 激活（**削瞬时峰值**） | 把 Prefill 的瞬时工作区从 `O(prompt²)` 压到 `O(block²)`；**累积 KV 终值不变**（[9-9](/training/p9/09-unaccounted)） |
| `前缀缓存模式` + `前缀块大小` | KV（**复用**） | 复用重复 prompt 前缀的 KV。⚠ 与分块预填充不同：**治重复计算，不治峰值** |
| `静态 VRAM 预分配` | 框架开销 | 一次性占池；`nvidia-smi` 看到的占用会大于真实需求 |
| `训练模式` | 权重 + 梯度 + 优化器 | 决定"可训练参数量"（[9-13](/training/p9/14-training-tuning)） |
| `LoRA 秩 r` / `挂载范围` | 梯度 + 优化器 | `L × 4 × 2 × h × r` 或含 MLP |
| `优化器类型` | 优化器状态 | `SGD 0 / SGD+M 4B / RMSProp 4B / AdamW 8B` |
| `8 项优化技术` | 激活 / 优化器 | 见下表 |
| `TP` / `PP` / `GPU 数` / `ZeRO 阶段` | 全部项摊分 | `÷ (TP × PP × [DP])` |
| `带宽效率系数` | 吞吐估算 | `带宽 ÷ 权重字节 × 系数` |
| `电价` / `碳强度` / `功耗` | 电费 / CO₂ | 见 [9-11b](/training/p9/12-cost-green) |

### 8 项优化技术在计算器里的作用

| 开关 | 计算器里的效果 | 依据 |
|---|---|---|
| `Flash Attention` | 训练激活 **× 0.75** | [9-7](/training/p9/07-activation) |
| `融合内核` | 训练激活 **× 0.92** | [9-13](/training/p9/14-training-tuning) |
| `动态填充` | 训练激活 **× 0.90** | 同上 |
| `序列打包` | **不改账本**（提升有效利用率） | 同上 |
| `梯度检查点` | 训练激活 **÷ √L** | [9-7](/training/p9/07-activation) |
| `8 位优化器` | 优化器状态 **× 0.25**（8 B → 2 B） | [9-8](/training/p9/08-optimizer-states) |
| `分页优化器` | **不改总量**（治碎片） | 同上 |
| `纯 16 位训练` | 优化器状态 **× 0.5** | 同上 |

::: warning ⚠ 三个系数的性质不同，别混看
- `×0.75 / ×0.92 / ×0.90`：**工程经验系数**（【推断】），不是公式推导出的精确值——它们只保证**同量级**
- `÷ √L`：**有代数依据**（[9-7](/training/p9/07-activation) 的分段重算）
- `×0.25`：**有字节依据**（8 B → 2 B，bitsandbytes 口径）

**所以计算器的输出是"量级估算"，不是"精确预测"**——这与 [9-9](/training/p9/09-unaccounted) 的立场一致。
:::

## (4) 判定词档位（⚠ 部分【待核实】）

计算器显存环右侧会给出一个**定性判定词**。界面实测确认的一档是：

| 占用率 | 判定词 | 状态 |
|---|---|---|
| 97.5%（31.2 / 32 GB） | **`非常高`** | ✅ 界面实测确认（微调页） |
| 16.1% | — | ❌ 该处 OCR 只读到标题，底端档位读不出 |

**本计算器采用的档表**（在界面实测前按"四档 + 单调"处理）：

| 档 | 阈值 | 判定词 | 建议动作 |
|---|---|---|---|
| 1 | ≤ 50% | `可以` | 余量充裕，可上更大并发 |
| 2 | 50 ~ 70% | `充足` | 可尝试加大 batch 或序列长度 |
| 3 | 70 ~ 90% | `偏高` | 预留 20% 余量，注意显存碎片 |
| 4 | > 90% | `非常高` | 已逼近上限，任何额外开销都会 OOM |

::: danger ⚠ 诚实声明
第 1~3 档的**用词未经界面确认**（首轮截图里见过 `可以`，但无法与具体占用率对应）。

- 本计算器的档表标为【推断】，与 9-A 词典中 `判定词档位` 条目的【待核实】标记一致
- **唯一被界面证实的事实**：`31.2 GB / 32 GB = 97.5%` 时显示 **`非常高`**
- 验收 gate 只断言"**档位数 ≥ 3 且单调**"，不断言具体用词（见 [9-15 验收 gate](/training/gate/README)）
:::

## (5) 吞吐怎么估的：decode 阶段的带宽上界

推理 decode 阶段（逐 token 生成）**是显存带宽瓶颈，不是算力瓶颈**——因为每生成 1 个 token，
都要把**整个权重**从显存读一遍：

```
带宽上界吞吐(t/s) = 显存带宽(GB/s) ÷ 权重(GB)
```

| GPU | 带宽 | 3B@INT8 权重 | 带宽上界 | 实测（界面） | 效率 |
|---|---|---|---|---|---|
| `RTX 5090 (32GB)` | `1792 GB/s` | 3 GB | **597 t/s** | **349 t/s** | 58% |
| `T4 (16GB)` | `320 GB/s` | 3 GB | 107 t/s | — | — |

`0.58` 这个效率系数就是**计算器里"估算吞吐"与"带宽上界"的比值**——它是一个可调的工程系数，不是常数。

**这就是为什么"量化能提速"**：权重从 6 GB（FP16）降到 3 GB（INT8），
带宽上界从 299 t/s **翻倍**到 597 t/s。**量化不止省显存，它同时抬高吞吐上限。**

## (6) 与正文的一致性（怎么验）

计算器的每个公式都在正文里有出处，可以逐条核对：

| 计算器行为 | 断言 |
|---|---|
| `n_kv = n_q` 时通式退化为 `2·L·h·s·b·C·B` | = 两篇参考的 MHA 公式（[9-5](/training/p9/05-kv-classic)） |
| `MLA` 的 KV = `L·d_c·s·b·C·B`，与 MHA 之比 ≈ `2h/d_c` | = `2 × 3072 / 576 = 10.67`（[9-14](/training/p9/15-end-to-end) 实测 10.7） |
| `CSA2` 的 KV = MLA `÷ 4` | 跨层复用 → 存储约 `1/4`（[9-6](/training/p9/06-kv-frontier)） |
| `DSA` 的 KV **与 MLA 相同** | 省带宽不省存储（同上） |
| 默认态（3B · INT8 · MLA · 4096）合计 ≈ **5.06 GB** | 界面 `5.1 GB`，偏差 **0.76%**（[9-14](/training/p9/15-end-to-end)） |
| QLoRA（r16 · 4bit · 4096）合计 ≈ **30.0 GB** | 界面 `31.2 GB`，偏差 **3.8%**（同上） |
| `TP×PP` 不整除 GPU 数时提示"配置无效" | 3D 网格必须可整除（[9-10](/training/p9/10-parallel-split)） |
| `ZeRO` 在 `DP = 1` 时对每卡值无影响 | ZeRO 是 DP 组内分片（同上） |

**这正是验收 gate 第 6、7 项在做的事**——把"计算器与正文一致"变成**可自动检查的断言**。

## (7) 纯 Python 复现（▶ 可运行）

不想开浏览器？同一套公式有一份无依赖的 Python 实现，用于 gate 校验：

```python
# p9/_calc/calc.py —— 与本页计算器同源
ATTN = ('MHA', 'GQA', 'MQA', 'MLA', 'SWA', 'DSA', 'CSA2')

def kv_bytes(attn, L, nq, nkv, h, dc, s, b, C, kb, win=None):
    d_head = h / nq
    if attn in ('MHA',):
        return 2 * L * nq * d_head * s * b * C * kb
    if attn in ('GQA', 'SWA'):
        eff = min(s, win) if (attn == 'SWA' and win) else s
        return 2 * L * nkv * d_head * eff * b * C * kb
    if attn == 'MQA':
        return 2 * L * 1 * d_head * s * b * C * kb
    if attn in ('MLA', 'DSA'):
        return L * dc * s * b * C * kb          # DSA 省带宽，不改存储
    if attn == 'CSA2':
        return L * dc * s * b * C * kb / 4      # 跨层复用 → ~1/4
    raise ValueError(attn)

def weight_bytes(params_B, nbytes):
    return params_B * 1e9 * nbytes

def lora_params(L, h, ffn, r, scope='attn'):
    if scope == 'attn':
        return L * 4 * 2 * h * r
    return L * (4 * 2 * h * r + 2 * (h * r + r * ffn) + (ffn * r + r * h))

def activation_train(s, b, h, L, grad_ckpt=False):
    a = 34 * s * b * h * 2 * L
    return a / (L ** 0.5) if grad_ckpt else a
```

**同时提供两条不可动摇的性质断言**（gate 会跑）：

```
① MHA 的 KV > GQA 的 KV > MQA 的 KV         （单调性）
② MLA 的 KV(FP16) > MLA 的 KV(INT8) > MLA 的 KV(INT4)   （位宽单调）
③ SWA 的 KV 不随 s 超过 W 而增长              （窗口饱和）
④ DSA 的 KV == MLA 的 KV                     （省带宽不省存储）
```

## 坑与自检

> ✕ 把计算器的数字当成"精确预测值"去下单。

> ✓ 它是**量级估算**（±20% 级），用于**比较方案**而不是**答应容量**。下单前无条件预留 2 GB（[9-9](/training/p9/09-unaccounted)）。

> ✕ 切了 `注意力机制结构` 却没注意 KV 项的变化量级。

> ✓ MLA / SWA 能带来**数倍**变化；DSA **一点都不降**（它省带宽）。

> ✕ 以为调大 `带宽效率系数` 就能提速。

> ✓ 它只是一个**系数假设**——真提速要靠降权重位宽（`带宽 ÷ 权重字节`）、换更高带宽的卡。

> ✕ 把"判定词"的档位当作界面事实引用。

> ✓ 只有 `非常高`（97.5%）是实测确认的；其余是本站【推断】，标【待核实】。

**自检清单**：

- [ ] 我能用这个计算器复现 [9-14](/training/p9/15-end-to-end) 的 **5.06 GB** 与 **30.0 GB** 两个数
- [ ] 我知道 **`MLA` 的 KV 只有 `MHA` 的约 1/10.7**，且计算器会直接提示倍数
- [ ] 我知道 `DSA` 在本计算器里 **KV 与 MLA 相同**（因为省带宽不省存储）
- [ ] 我知道 `序列打包` 开关 **不改账本**（它提有效利用率）
- [ ] 我知道 **带宽上界吞吐 = 带宽 ÷ 权重字节**，量化能让它翻倍
- [ ] 我知道判定词的 4 档里只有 `非常高` 是实测确认的
