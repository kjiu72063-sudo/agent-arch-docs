# 9-9 · 算不到的那部分：框架开销、预分配、多GPU开销

::: info 难度分层 · 本页 = L3（可算层）
L3 能说清"**为什么算出来够、一跑就 OOM**"，并知道该预留多少、该关哪个开关。★★★
:::

## 定位

[9-3](/training/p9/03-weights-params) 到 [9-8](/training/p9/08-optimizer-states) 算的都是"**能建模的账**"。
真实的 OOM 大多发生在**算不出来的那几项**上。本页把它们摊开。

## (1) 框架开销：唯一"占比高却无人讲"的一项

| 项 | 说明 |
|---|---|
| 是什么 | CUDA 上下文、框架自身（PyTorch/TensorFlow）、当前批次的输入缓冲 |
| 经验值 | **1 ~ 2 GB**（【业界口径】阿里云 PAI 原文） |
| 计算器实例 | **1.01 GB ≈ 19.6%**（占 5.1 GB 总占用的近五分之一） |
| 能消除吗 | **不能**——只能预留 |
| 课程覆盖 | ❌ **0 命中** |
| 三篇参考覆盖 | 阿里云给了区间；CSDN-leo0308 未给数值（速查表注明"受框架 Overhead 影响可能波动 10-20%"）；CSDN-weixin 明确写"**一些临时显存占用，先不计算**" |

::: danger ⚠ 这是"算够了却 OOM"的头号原因
把 [9-2](/training/p9/02-ledger-overview) 的账算得再准，**漏掉这 1~2 GB 就可能刚好卡在临界点上**。

**真实案例的量级**：假设你算出来 30.5 GB，卡是 32 GB，你判断"够"。
加上框架开销 1.5 GB → **32 GB，正好爆**。再叠加显存碎片 → 提前 OOM。

**行动项**：容量规划时**无条件预留 2 GB**，不要用"刚好够"的结论去下单。
:::

## (2) 静态 VRAM 预分配

| 项 | 说明 |
|---|---|
| 做法 | 进程启动时**一次性占满**一大块显存（预分配池），后续在池内分配 |
| 收益 | 避免**运行时**反复 `cudaMalloc` 带来的碎片与时延尖刺 |
| 代价 | 从外部看"显存被占满"，**实际空闲**；多进程共享一张卡时容易误判 |
| 计算器字段 | `静态 VRAM 预分配`（开 / 关） |
| 该什么时候开 | 服务常驻、显存独享 → **开**；共卡、需要弹性 → **关** |

> 这也是为什么 `nvidia-smi` 看到的占用常常**大于**模型实际需求——不全是"浪费"。

## (3) 多 GPU 开销：三篇参考全无的一项

**这一项必须诚实标注**：【推断】。

| 项 | 说明 |
|---|---|
| 由什么构成 | 集合通信缓冲（AllReduce/AllGather 的临时张量）+ 每卡参数/状态的**副本** |
| 为什么没有统一公式 | 与并行策略（TP/PP/DP）、通信后端（NCCL/Gloo）、`bucket` 大小、重叠策略**强相关** |
| 粗略量级 | 与**通信量**同阶；参考 [4-7 集合通信原语](/training/p4/07-primitives) / [4-8 AllReduce](/training/p4/08-allreduce) 的 `2(N−1)/N·Ψ` |
| 单项 vs 多卡 | **单卡（`1 GPUs`）时账本里有这一项但接近 0** |
| 谁讲了 | ❌ **阿里云 / CSDN-leo0308 / CSDN-weixin 三篇齐缺** |

**怎么估**：单卡可以忽略；多卡时按"**通信缓冲 ≈ 一个 bucket 大小的若干倍**"预留，
并结合 [4-12 ZeRO](/training/p4/12-deepspeed-zero) 的通信量公式判断量级。

## (4) 分块预填充（Chunked Prefill）

计算器「高级配置」组里的一个开关，配一个数值字段：

| 字段 | 界面说明（原文） | 默认值 |
|---|---|---|
| **分块预填充** | — | 开 / 关 |
| **预填充分块大小** | 提示词处理期间每块的 Token 预算 | **2,048 tokens** |

**机制**：Prefill 阶段把整段 prompt 一次性喂进去算 KV，此时会同时产生两类占用——

| 占用 | 量级 | 分块预填充能压吗 |
|---|---|---|
| **累积 KV** | `O(L_prompt)` | ❌ **终值不变**（一块块累积上去，最后还是整段） |
| **瞬时注意力工作区** | **`O(L_prompt²)`** | ✅ **能，降到 `O(block²)`** |

分块预填充把 prompt 切成 2,048 token 一块**逐块处理**，于是**瞬时峰值从"整段 prompt 的平方"降到"一块的平方"**：

| prompt 长度 | 不分块的瞬时工作区 ∝ | 分块后 ∝ | 削减倍数 |
|---|---|---|---|
| 4,096 | 16,777,216 | 4,194,304 | **4×** |
| 16,384 | 268,435,456 | 4,194,304 | **64×** |
| 65,536 | 4,294,967,296 | 4,194,304 | **1,024×** |

> ⚠ **一句话分清**：分块预填充削的是**瞬时峰值**，**不是稳态 KV**。
> prompt 越长，收益越大——这正是它存在的理由。

| 项 | 不分块 | 分块（block = 2048） |
|---|---|---|
| 累积 KV 终值 | `O(L_prompt)` | `O(L_prompt)`（**不变**） |
| **瞬时注意力工作区** | **`O(L_prompt²)`** | **`O(block²)`** ← 省的就是它 |
| 首 token 延迟 TTFT | 低 | **略升**（要跑多轮） |
| 与 Decode 混跑 | 容易互相饿死 | **可与 decode 交错**，吞吐更稳 |

::: warning ⚠ 别和"前缀缓存"搞混
- **分块预填充（chunked prefill）**：把**一次** prefill 切成多块 → 治**峰值**
- **前缀缓存（prefix caching）**：把**重复的** prompt 前缀 KV 存下来复用 → 治**重复计算**

两者都在计算器的 `高级配置`/`高级运行时设置` 区域，但目的完全不同。
:::

## (5) 卸载到 CPU / RAM / NVMe

计算器里一个横跨推理与微调两侧的开关：`启用卸载到 CPU/RAM 或 NVMe`。

```mermaid
flowchart LR
  G["GPU 显存<br/>最快、最小"] --> C["CPU / RAM<br/>中等、较大"]
  C --> N["NVMe SSD<br/>最慢、最大"]
  W["权重 / 优化器状态 / KV"] --> G
  G -.->|"放不下就下沉"| C
  C -.->|"还放不下再下沉"| N
  style G fill:#4f46e5,color:#fff
  style C fill:#b45309,color:#fff
  style N fill:#8b1a1a,color:#fff
```

| 层级 | 速度 | 容量 | 适合放什么 |
|---|---|---|---|
| GPU 显存 | 最快 | 最小 | 前向/反向要频繁访问的（权重、当前层激活） |
| CPU / RAM | 中 | 大 | **优化器状态**（每步只用一次） |
| NVMe SSD | 最慢 | 最大 | 冷数据 / 检查点 |

【业界口径】CSDN-weixin：

> 如果显存还不够，就只能采用 Memory Offload 的技术，把部分显存的内容给挪到内存，但是这样会**显著降低推理速度**。

【业界口径】CSDN-leo0308：

> **DeepSpeed ZeRO-2 Offload**：只有一张消费级显卡（如 12G 的 3060）想跑大一点的模型？开启 DeepSpeed 的 Offload 功能，把**优化器状态踢到 CPU 内存**里，能救命。

**已覆盖现状**：讲义 [4-13 FSDP](/training/p4/13-fsdp) 讲了 FSDP 的 CPU offload，但**没有 NVMe 三级卸载**。

## (6) 显存碎片

| 项 | 说明 |
|---|---|
| 现象 | 总量够，但**没有连续块**可分配 → OOM |
| 常见诱因 | 反复 `cudaMalloc`/`free`、变长序列、动态 shape |
| 对策 | **静态预分配**（防碎片）+ **分页优化器**（治优化器侧碎片）+ **分块 KV Cache**（治 KV 侧碎片，见 [6-8](/training/p6/08-vllm-pagedattention)） |
| 特点 | **不可精确计算**，只能通过"预留 + 用对开关"规避 |

## (7) 汇总：容量规划的"预留清单"

| 项 | 建议预留 | 性质 |
|---|---|---|
| 框架开销 | **2 GB** | 经验值，不可消除 |
| 多 GPU 开销 | 单卡 0；多卡按通信量估算 | 无公开口径 |
| 显存碎片 | **5% ~ 10%** | 不可精确计算 |
| 预分配池 | 按服务模式决定开/关 | 开关型 |
| 峰值波动 | 按 `b × s` 的最大值而非平均值算 | 常见误算点 |

::: tip 一条务实的经验法则
**"算出来 ≤ 卡显存的 85%" 才算真的够。** 剩下的 15% 就是给上面这些"算不到的部分"留的。
:::

## 决策表：算够了还是 OOM，逐项排查

| 排查顺序 | 查什么 | 怎么查 |
|---|---|---|
| ① | 是否漏算了**框架开销**（1~2 GB） | 加 2 GB 重算 |
| ② | 是否用了**平均** `s` 而非**峰值** `s` | 取最长序列重算 |
| ③ | 是否漏了**并发** `C` | 见 [9-6](/training/p9/06-kv-frontier) |
| ④ | 是否**静态预分配**占满 | 关闭后看实际占用 |
| ⑤ | 是否**多卡通信缓冲**没预留 | 单卡对比验证 |
| ⑥ | 是否**碎片** | 开静态预分配 / 分页优化器试 |
| ⑦ | Prefill 峰值是否过大 | 开**分块预填充** |
| ⑧ | 还差很多 | 上**卸载**（CPU → NVMe） |

## 坑与自检

> ✕ 算出来 30.5 GB、卡 32 GB，就下结论"够"。

> ✓ 加 **2 GB 框架开销** + **5~10% 碎片**，"够"的门槛是 **≤ 85% 卡容量**。

> ✕ 把分块预填充和前缀缓存当同一件事。

> ✓ 分块预填充治 **Prefill 峰值**；前缀缓存治 **重复计算**。

> ✕ 以为 `nvidia-smi` 显示的占用全是模型在用。

> ✓ 可能包含**静态 VRAM 预分配**的空池。

> ✕ 以为卸载是"免费的显存扩容"。

> ✓ 卸载**显著降低速度**（尤其 NVMe 层）。

**自检清单**：

- [ ] 我知道框架开销经验值 **1~2 GB**，且三篇参考中只有阿里云给了数值
- [ ] 我知道**多 GPU 开销无公开口径**，属【推断】
- [ ] 我能说清**分块预填充** vs **前缀缓存**的区别
- [ ] 我知道卸载有三层（显存 / CPU-RAM / NVMe），且 NVMe 层最慢
- [ ] 我会用"**≤ 85% 卡容量**"作为"够不够"的判据
