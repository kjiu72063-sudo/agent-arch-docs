# 9-12 · 推理调参手册：6 个旋钮 + 4 组预设

::: info 难度分层 · 本页 = L3（可算层 → 决策层）★速查
本页是**全模块的操作页**：前面 11 页都在算"哪一项多大"，本页回答"**该动哪一个**"。
读完你应能在 30 秒内对任意约束说出：动哪个旋钮、省多少、代价是什么。★
:::

::: tip 本页用的是「调参手册模板」，不是正文的七段式
```
目标 → 候选旋钮（按性价比排序）→ 每个旋钮的显存收益 / 时延代价 / 质量风险 → 组合建议 → 反例
```
与 [9-13 训练调参手册](/training/p9/14-training-tuning) 同构。
:::

## (0) 先明确目标：你要优化的是哪个指标

**调参不是"越大越好"，是先确定目标函数。** 计算器的两个弹窗就是在替你做这件事：

| 弹窗 | 预设按钮 | 目标函数 |
|---|---|---|
| 「优化 Custom Model 以在 RTX 5090 上运行」 | `自动适配` / `最佳精度` / `最大上下文` / `最高吞吐量` | **在给定卡上找可行解** |
| 「查找运行 Custom Model 的配置」 | `最低成本配置` / `最大吞吐量` | **在给定预算下找最便宜的卡** |

> 前者是"**卡已定，调参数**"；后者是"**参数已定，挑卡**"。这是两个反方向的搜索，别混用。

## (1) 6 个旋钮：按性价比排序

| 序 | 旋钮 | 影响账本哪一项 | 收益量级 | 时延代价 | 质量风险 | 出处 |
|---|---|---|---|---|---|---|
| **K1** | **推理量化**（权重精度） | ① 权重 | FP16→INT8 **−50%**；→INT4 **−75%** | 通常**提升**（带宽降、算力升） | **中**（低比特影响精度） | 计算器 `推理量化` |
| **K2** | **KV 缓存量化** | ② KV Cache | FP16→INT8 **−50%**；→INT4 **−75%** | 略降 | **中低**（长序列更敏感） | 计算器 `KV 缓存量化` |
| **K3** | **注意力机制结构** | ② KV Cache（**改公式形态**） | GQA `×g/n_q`；MQA `×1/n_q`；MLA 换潜变量式；SWA O(L)→O(W) | 视结构而定 | **低**（模型自带，非运行时选项） | [9-5](/training/p9/05-kv-classic) / [9-6](/training/p9/06-kv-frontier) |
| **K4** | **序列长度 / 上下文** | ② KV + ③ 激活 | **线性**（SWA 下**饱和**） | 长上下文 TTFT 升 | 无（是需求，不是优化项） | 计算器 `序列长度` |
| **K5** | **批量大小 × 并发用户数** | ② KV + ③ 激活 | **线性乘数**（两个独立乘数） | 批大→吞吐升、单请求延迟升 | 无 | 计算器 `批量大小` / `并发用户数` |
| **K6** | **并行切分（TP/PP）× 卸载** | 全部项摊分 / 换出 | TP/PP **÷ 维度**；卸载把整项换出到 CPU/NVMe | **明显**（通信或 PCIe） | 无 | [9-10](/training/p9/10-parallel-split) / [9-9](/training/p9/09-unaccounted) |

::: warning 排序逻辑：为什么 K1、K2 排在前面
**性价比 = 省得多 ÷ 代价小**。

- **K1 量化**：省 **50~75%** 的权重，代价是"可能降一点质量"——**没有任何通信或延迟惩罚**，甚至更快。
- **K2 KV 量化**：只动 KV 项，但 KV 在长上下文下会**反超权重**（[9-6](/training/p9/06-kv-frontier)），所以它的收益**随序列长度上升**。
- **K3 注意力结构**：收益可能最大（MLA/SWA/CSA2 都是数倍级），但它是**模型选型时的决定**，不是运行时能拧的旋钮——列入本表是为了让你在**选模型时**就把它算进账。
- **K6 并行**：能省任何一项，但**省多少就要付多少通信**，是最后手段。

**一句话**：**先量化，再限上下文，最后才上多卡。**
:::

## (2) 逐个旋钮：收益 / 代价 / 副作用

### K1 推理量化（权重精度）

| 档位（计算器弹窗口径） | 字节/参数 | 3B 模型权重 | 相对 FP16 |
|---|---|---|---|
| `完整(FP16)` | 2 B | 6.0 GB | 基准 |
| `FP8` | 1 B | 3.0 GB | **−50%** |
| `Q4(INT4)` | 0.5 B | 1.5 GB | **−75%** |

> ⚠ 计算器有**两套口径**：主界面写 `INT8 / FP16·BF16`，配置弹窗写 `完整(FP16) / FP8 / Q4(INT4)`。
> 用的时候以**弹窗**为准（它有完整三档），主界面只是展示态。**FP8 三篇参考全无**（[9-A 词典](/training/p9/16-calculator) 标【推断】）。

**关键**：量化只影响**权重项**，对 KV 与激活**没有**帮助。
所以"量化后显存还是不够"的唯一原因，是**KV 或激活撑爆了**（长上下文场景最常见）。

### K2 KV 缓存量化

| 档位 | KV 字节/token | 相对 FP16 |
|---|---|---|
| `FP16 / BF16` | 2 B | 基准 |
| `INT8` | 1 B | **−50%** |
| `INT4` | 0.5 B | **−75%**（前沿已到 **FP4**，见 [9-6](/training/p9/06-kv-frontier)） |

**这是长上下文里性价比最高的旋钮**——它**只砍 KV**，不动权重、不动激活。

| 场景 | 该不该开 |
|---|---|
| 短上下文（≤4K）、权重占大头 | 收益小，可不开 |
| **长上下文（≥16K）、KV 反超权重** | **强烈建议开** |
| 精度极敏感（代码/数学推理） | 先 FP16 基线，再逐档回退验证 |

### K3 注意力机制结构（选模型时决定）

七档的 KV 体积对比（详细推导见 [9-5](/training/p9/05-kv-classic) / [9-6](/training/p9/06-kv-frontier)）：

| 档 | KV 形态 | 相对 MHA |
|---|---|---|
| **MHA** | `n_kv = n_q` | **1×**（最大） |
| **GQA** | `n_kv = g` | **`g/n_q`**（参考文称 **4–8 倍**降幅） |
| **MQA** | `n_kv = 1` | **`1/n_q`** |
| **MLA** | 存**潜变量** `d_c = 512 + 64 = 576` | 与 `n_q` **解耦**，公式形态不同 |
| **SWA** | 有效长度 `min(s, W)` | **省存储**（O(L)→O(W)） |
| **DSA** | 存储**不变** | **省带宽**（每步只读 top-K 个条目） |
| **CSA2** | 跨层复用 global KV | **省存储**（约 **1/4**；配 FP4 → 约 **1/8**） |

::: danger ⚠ 本模块最重要的一条选型判据
**「省显存」和「省带宽」是两件事。**

- 你的瓶颈是**装不下**（OOM）→ 看 **SWA / CSA2 / GQA / MQA / MLA / KV 量化**
- 你的瓶颈是**跑得慢**（长上下文时延）→ 看 **DSA**（KV 还在，但每步只读 top-K 个）

**把 DSA 当"省显存"用会误判**——它不降低 KV 占用。
:::

### K4 序列长度 / K5 批量与并发

两者都是 **KV 与激活的线性乘数**，差别在于"谁在乘"：

```
KV Cache = 2 × L × n_kv × d_head × s × b × C × bytes
                                     ↑    ↑   ↑
                                   序列  批  并发用户数
```

| 旋钮 | 乘的是 | 特点 |
|---|---|---|
| 序列长度 `s` | KV、激活 | 由**业务需求**决定（上下文要多长），不是优化项 |
| 批量大小 `b` | KV、激活 | 提吞吐的主手段，但线性吃显存 |
| **并发用户数 `C`** | KV（**乘数**） | ★ 计算器有独立字段，用**对数刻度**——因为它是"同时服务多少人" |

::: danger ⚠ 并发用户数是 KV 的"隐藏乘数"
很多人算显存时只算 `b = 1`，一上线并发 8 就 OOM。

**KV 正比于 `b × C`**——`并发 8 × 批 1` 与 `并发 1 × 批 8` 在 KV 上**等价**。
但两者对**延迟**的影响完全不同：前者是 8 个用户各等各的，后者是 8 条样本攒成一个 batch 一起算。

**行动项**：算 KV 时问自己"**峰值同时几个人在跑**"，把它乘进去。
:::

### K6 并行切分与卸载（最后手段）

| 手段 | 省什么 | 代价 | 什么时候用 |
|---|---|---|---|
| **TP** | 权重、KV（÷ TP） | 每层两次 AllReduce，**必须高带宽/NVLink** | 单卡装不下、但有 NVLink |
| **PP** | 权重（÷ PP） | 流水线气泡 | 跨机 |
| **卸载到 CPU/RAM/NVMe** | 换出整项 | **PCIe/NVMe 带宽瓶颈，显著降速** | 实在装不下、且能容忍慢 |
| **分块预填充**（block 2048） | 削 **Prefill 峰值** | TTFT 略升 | 长 prompt + 高并发混跑 |

> 卸载"显著降速"——CSDN-weixin 原文；【业界口径】计算器 `启用卸载到 CPU/RAM 或 NVMe` 开关。

## (3) 4 组预设：计算器替你做的取舍

「优化 X 以在 Y 上运行」弹窗给了 4 个按钮。它们的本质是**在四个不同的约束下求解**：

| 预设 | 约束（谁被固定） | 放开什么 | 典型结果 |
|---|---|---|---|
| **`自动适配`** | 卡固定 | 全部参数，求**可行解** | 精度尽量高、能装下就行 |
| **`最佳精度`** | 卡 + 上下文固定 | 只降精度到刚好装下 | FP16 优先，装不下才退 |
| **`最大上下文`** | 卡 + 精度固定（**降到 INT4**） | 把上下文顶到最大 | 示例顶到 **32,768** |
| **`最高吞吐量`** | 卡 + 精度固定 | 调 batch / 序列求 **t/s 最大** | 示例 **2,048 / batch 1 / INT4** |

**计算器实测的三张预设卡**（同一个 `Custom Model` 在 `RTX 5090 (32GB)` 上）：

| 卡片 | 上下文 | Batch | 精度 | 吞吐 | 说明（原文） |
|---|---|---|---|---|---|
| **FP16 Quality** | `4,096` | 1 | `FP16` | `~341 t/s` | *Highest supported precision (FP16) fitting within memory.* |
| **最大上下文** | **`32,768`** | 1 | INT4 | `~358 t/s` | *Maximum feasible context window using INT4 precision.* |
| **1 Batch @ INT4** | `2,048` | 1 | `INT4` | `~362 t/s` | *Peak throughput configuration yielding estimated tokens/sec.* |

::: tip 读这三张卡能读出什么
1. **精度从 FP16 降到 INT4，吞吐只从 341 涨到 362（+6%）**——说明**吞吐瓶颈不在精度**，而在别处。
2. **上下文从 4,096 顶到 32,768（8 倍），吞吐只掉 341→358**——说明**这个模型在 5090 上远没有触及算力天花板**（3B 小模型 + 0.1B 激活）。
3. **三张卡都是 `Batch = 1`**——说明在这个评估里，**加 batch 不如加并发**（或者说 batch 上不去受显存/延迟约束）。

**这正说明：预设不是"哪个更快"，而是"哪个约束你更在意"。**
:::

### 另一组预设：`最低成本配置` / `最大吞吐量`

来自「查找运行 Custom Model 的配置」弹窗——注意它评估的规模完全不同：

| 项 | 读数 |
|---|---|
| 评估规模 | **评估了 3,960 个配置** |
| 精度约束 | `完整(FP16)` / `FP8` / `Q4(INT4)` |
| 硬件类型 | `Nvidia` |
| SLA / 预算约束（PRO） | 按**延迟目标、小时成本限制或最低速度**过滤 |
| 推荐结果 | `1x T4 (16GB)` · `$0.12/hr` · `382.5–467.5 t/s` · `4.1 GB / 16.0 GB` · `已用显存 26%` |
| 备选表 | 列：**配置 / 量化 / 每小时成本 / 速度与延迟 / 与推荐配置相比 / 应用** |
| 底部 | `显示所有 104 个备选配置` |

**备选表示例行（能看出"比推荐配置"这列在说什么）**：

| 配置 | 量化 | $/hr | 速度与延迟 | 与推荐配置相比 |
|---|---|---|---|---|
| `1x T4 (16GB)` | FP16 | `$0.12/hr` | — | 成本相同，**吞吐量降低 5%** |
| `1x RTX 3060 Ti (8GB)` | — | `$0.15/hr` | `48 ms TTFT` | **成本高出 25%**，吞吐量降低 30% |
| `1x RTX 3070 (8GB)` | — | `$0.17/hr` | `268.2–327.8 t/s` | **成本高出 42%** |
| — | — | `$0.20/hr` | `282.6–345.4 t/s`，`38 ms TTFT` | **成本高出 67%**，吞吐量降低 26% |

::: warning ⚠ 为什么"最便宜"和"最快"经常是同一张卡
因为 **$/百万 token 与吞吐成反比**（[9-11b](/training/p9/12-cost-green)）：

```
$/百万token = 租金 ÷ (吞吐 × 3600) × 1e6
```

`1x T4` 的 `$0.12/hr × 425 t/s` 换算下来是 **$0.0784/百万 token**，
而 `RTX 5090` 的 `$1.10/hr × 349 t/s` 是 **$0.8755/百万 token**——**差 11 倍**。

**所以「最低成本配置」往往同时是「最大吞吐量配置」**，只要你的 SLA 不要求低 TTFT。
这两组预设不矛盾：**它们的分歧点全在延迟约束上**。
:::

## (4) 组合建议：三种典型约束的配方

| 你的约束 | 配方（按顺序拧） | 预期结果 | 代价 |
|---|---|---|---|
| **"32GB 卡要跑 33K 上下文"** | ① K1 降到 INT8 → ② K2 KV 降到 INT8 → ③ 开 **SWA / 限窗口** → ④ 还不行才卸载 | KV 与权重同时砍半，加上窗口饱和 | ③ 让长上下文"看得见但读不全" |
| **"单卡想跑满并发，成本最低"** | ① K2 KV 量化 → ② 选 **GQA/MQA/MLA** 的模型 → ③ 分块预填充削峰值 | KV 大幅下降，并发上得去 | 低比特 KV 的精度 |
| **"TTFT 必须 < 50ms"** | ① 换 **更高带宽的卡**（不省显存，省时间）→ ② **不开**卸载 → ③ 少开 PP（气泡） | 首字延迟达标 | 硬件成本 |

::: tip 一个反向的自检
**如果拧完 6 个旋钮显存还是不够，说明问题不在参数上，在"选型"上。**
真正的解法是换模型（更小、或 KV 结构更省的），或者承认这张卡跑不了这个组合。
——这时该回看 [9-1](/training/p9/01-first-constraint) 的决策链，而不是继续拧旋钮。
:::

## (5) 反例（三个最常见的错误配方）

> ✕ **一上来就上多卡（TP/PP）** —— 应该先把量化拧到底、把上下文定清楚，多卡是最后手段。

> ✓ 顺序：**K1 → K2 → K3（选模型）→ K4/K5（定需求）→ K6（多卡/卸载）**。

> ✕ **量化了权重就以为显存够了** —— 长上下文时 KV 反超权重；量化权重对 KV **零帮助**。

> ✓ 长上下文必开 **KV 量化**，或换 **SWA/MLA/CSA2** 结构的模型。

> ✕ **按 `b = 1` 算显存就下单** —— 上线并发 8 就 OOM。

> ✓ 把 **并发用户数 `C`** 乘进 KV（它是独立字段，不是 batch 的别名）。

## 坑与自检

- [ ] 我能背出 6 个旋钮的**优先级顺序**：量化 → KV量化 → 结构 → 上下文 → 批/并发 → 并行/卸载
- [ ] 我知道 **K1 只省权重、K2 只省 KV**，两者互不替代
- [ ] 我知道 **并发用户数是 KV 的独立乘数**，不能按 `b=1` 算
- [ ] 我能解释**为什么"最低成本"和"最大吞吐"常是同一张卡**（$/百万 token 与吞吐成反比）
- [ ] 我能说出 **DSA 省带宽不省存储**，不能用它解决 OOM
- [ ] 我能在"32GB 跑 33K 上下文"这个约束下说出前 3 步配方
