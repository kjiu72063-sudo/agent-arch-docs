# 验收脚本（gate）· 训练·微调·部署模块

> **边界声明（务必先读）**
>
> 本模块的 gate **只验证「数学上或结构上确定」的东西**——
> 算术一致性、公式代入、Schema 合法性、布尔互斥、张量形状。
>
> **不验证**：训练效果、微调收益、推理质量、加速倍数、显存实测占用。
> 这些属于**实测范畴**，本站只给方法与预期区间，**不提供 gate**。
> 这与 Agent 模块 `loop_gate` 的诚实边界一脉相承（「只验证确定性控制流，不验证 LLM 产出质量」）。

## 运行

```bash
python training/gate/run_all_gates.py
```

零第三方依赖（纯标准库）。若本机装有 `torch`，`gate_10` 会自动追加一条
「纯标准库 ↔ torch 双路径互证」，未安装则跳过并仍自洽。

### 第 24 项为什么是整个 Part 9 最特殊的一个

方案 §8 把它写成一句话：

> **参数词典完整性：计算器字段清单 ⊆ 词典条目（防止漏讲）**

它把「**大纲/讲义里没讲的参数必须被指出来**」这个原本靠人肉核对的要求，
变成了**一条可自动执行的集合包含断言**：

```
p9/_calc/fields.py    ← 计算器 85 个字段的机器可读清单（id / label / 分组 / 分类）
        ⊆
p9/A-param-dict.md    ← 《参数词典》正文（85 个词条逐条子串命中）
```

任何一次「新增了计算器字段但忘了写进词典」都会让它**立刻红**。
同时它还断言：

- 正文的统计表与 `fields.py` 的计数一致（防止文档与清单脱钩）
- 3 处**次生参数**（`模态` / `线性注意力比例` / `启用高范围累积步数`）必须被显式标为「本模块未展开」
  —— 即**不冒充权威补公式**（R3 规则的落地）
- 判定词档表「档数 ≥ 3 且单调」，但**不断言具体用词**（因为界面只实测到 `非常高` 一档）

## 附：术语与口径对照（Part 9 特有）

Part 9 引入了三处**必须显式声明**的口径，gate 会对它们做断言：

| 口径 | 主口径 | 脚注口径 | 差 | 断言位置 |
|---|---|---|---|---|
| **优化器状态** | 阿里云 8 B/参数（56 GB @7B） | CSDN 12 B/参数（含 fp32 主权重，84 GB） | 恰 4 B/参数 | gate_17 |
| **训练静态账** | 阿里云 12 B/参数（87.4 GB @7B） | CSDN 16 B/参数（112 GB） | 24.6 GB | gate_17 / gate_20 |
| **激活值** | 10%（阿里云，`b=1,s=2048` 条件） | 20–30%（CSDN，长上下文） | 双档 | gate_16 / gate_18 |
| **单位** | 引用阿里云数字标 `GB`（十进制） | 本站计算标 `GiB`（二进制） | 7% | 全模块 |

**三处口径冲突一律不"和稀泥"**——给双档 / 标主辅，并说明差异来源。

## 构建侧辅助（不是 gate，但强烈建议跑）

Mermaid 语法错误**不会让 `vitepress build` 失败**——它只在浏览器运行时抛错，
页面上的图会变成一块红色报错块。所以「构建绿灯」≠「图能画出来」。

```bash
node scripts/check-mermaid.mjs          # 默认扫描**全站**所有 md（两个模块一起）
node scripts/check-mermaid.mjs training # 只校验指定目录
```

它用项目自带的 mermaid 解析器（与站点运行时同版本）把每张图 parse 一遍。

运行结果：

- 新建的训练模块：首次抓出 **3 张真实语法错误**，根因都是**标签里嵌了直引号**
  （`Q2{"是"事实"还是"模式"？"}`）——改成 `「」` 后全部通过。
- **Agent 模块发现 1 处历史遗留**：`start/06-overview.md:27` 的 `S -. .-> L`
  少了连字符（应为 `S -.-> L`），会让整张图在浏览器里报错。
  **按方案 §7「不改动 Agent 模块正文」的约定，此处只报告、未改动**，等你点头再修。

> **Part 9 新增页面的 Mermaid 规则（踩过坑）**：
> `flowchart` 的节点标签里**绝不能出现直引号 `"`**——包括在 Python 里用 f-string
> 写 gate 的 `print` 时也要小心（本轮的 gate_18 / gate_22 就因此报过语法错误）。
> 需要强调时统一用 `「」` 或 `【】`。

### Part 9 新增的检出（gate_13 ~ gate_24 的副产品）

| 检出点 | 说明 |
|---|---|
| **计算器「总参数量」与架构字段不自洽** | `gate_13` 证明：由 `32 层 / 3072 / 18944 / 152064` 反推得 **7.26B**，而界面标签写 **3B**（**+142%**）。两条数据链（标签链管权重、架构链管 KV）各自自洽但**互不校验**——所有显存计算器的通病 |
| **两篇参考的 KV 公式都缺 `n_kv` 因子** | `gate_14` 证明：`n_kv = n_q` 时通式才退化为两文给出的式子（隐含 MHA）。用它算 GQA 会**高估 4–8 倍**，算 MLA 会**高估 10–25 倍** |
| **DSA 不省显存** | `gate_14` 断言 `KV(DSA) == KV(MLA)`：它省的是**带宽**（每步只读 top-K），不是**存储**。这是选型误判的头号来源 |
| **计算器的激活项用的是 30% 档** | `gate_18` 由残差反推（`0.939 / 3.0 = 31.3%`）；若按阿里云 10% 档则与界面差 **12.53%** |
| **QLoRA 的瓶颈是激活值，不是权重** | `gate_19` 证明激活占 **91.2%**，而权重+梯度+优化器只占 **5.4%**——「QLoRA 跑不动」通常被误诊为模型太大 |
| **单卡开 ZeRO 等于没开** | `gate_19` / `gate_20` 断言 `DP = 1` 时 ZeRO-1/2/3 的每卡值与不启用完全相同 |
| **分块预填充削的是瞬时峰值** | `gate_22` 区分：累积 KV 终值 **O(prompt) 不变**，被削的是**瞬时注意力工作区 O(prompt²) → O(block²)**（4K/16K/64K 分别省 4× / 64× / 1024×） |
| **界面读数存在取整** | `gate_23` 反推：CO₂ 界面显示 `475 g/kWh`，实际为 **475.26**；训练时长界面显示 `5.7h`，两个单价各自反推为 **5.664 / 5.668 h**（彼此一致） |
| **计算器缺两处字段说明** | `check-mermaid` / `gate_22` 交叉发现 `9-15` 的控件表漏了 `分块预填充` 与 `前缀缓存模式`（**已补**） |
