# D6 · 贯穿机制：环境层 / 证据层 / 控制层

> 这三层**不是独立阶段**，而是"S0–S5 每个阶段都要遵守"的横切要求。
> **理论锚点**：环境层直接对应 [03 harness 七大核心组件](/concepts/harness/mechanism)，但**证据层与控制层是 Track D 独有**。

---

## 贯穿机制 A：环境层

> 这一章是每个阶段都要遵守的 **Agent 可靠性要求**——"这个阶段如何以 Agent 可执行的方式交付"。

### A.1 上下文工程：AGENTS.md 写地图，不写百科全书 `[书 p6-7 p17-19]`

> 核心原则：**Agent 应当恰好获得当前任务所需的上下文——不多不少。**

**三层上下文体系** `[书 p7]`：

| 层级 | 加载时机 | 内容 | 占用 |
|---|---|---|---|
| **Tier 1 会话常驻** | 每次会话自动加载 | `AGENTS.md` / `CLAUDE.md`、项目结构概览 | 最小 |
| **Tier 2 按需加载** | 特定子 Agent 或技能被调用时 | 专业化 Agent 上下文、领域知识 | 中等 |
| **Tier 3 持久化知识库** | Agent 主动查询时 | 研究文档、规格说明、历史会话 | 按需 |

**落地铁律** `[推]`：Tier 1 只放"**地图**"和"**硬性规则**"；任何内容一旦超过容量预算，**必须下沉到 Tier 2/3 并在 Tier 1 留一行链接**。

**四条设计原则** `[书 p19]`：

1. 控制在 **50–100 行**（⚠️ 此条在实际仓库被证伪，见下方"诚实提示"）
2. **"你想做什么 → 去哪里看"比"这是什么"更有效**——面向任务而非面向知识
3. **硬性规则单独列出**，这些是 CI 会强制验证的，**不是"建议"**
4. 每份文档头部加元信息（`last_updated / status / owner`），让**文档园丁**能扫过期

::: warning 诚实提示：这一条被实际证伪了
教材说"AGENTS.md ≤100 行"。但**实际工程仓库的 `AGENTS.md` 达 16KB ≈ 400+ 行，项目正常运行**。原因：该文件含**导航表 + 硬性规则 + 纪律段 + 踩坑索引 + 目录结构**——其中**导航类内容并不挤占"正事"空间**。

**结论：本规则应降级为「提醒」，不是硬律。**
真正的判据是：**有没有挤掉"正事"**，而不是行数。详见 [D8 验证台账](/process/tooling)。
:::

### A.2 约束工程：错误信息即 Prompt `[书 p23-25]`

> 这是 Harness Engineering **最有杠杆的实践之一**。每条 Linter 报错都必须包含三要素——**问题是什么、怎么修、去哪看文档**。

**万能公式**：

```
❌ [什么错了]
✅ FIX: [怎么改，给出代码片段]
📖 See: [哪个文档有详细说明]
```

> **Agent 看到这种报错，不需要任何额外提示就能自动修复。你写的每一条 Linter 规则，本质上都是一个自动触发的 Prompt。**

**⚠️ Python 实现的两层策略** `[推]`（重要工程细节）：

> **现实约束**：Ruff 的规则消息**不允许任意自定义文本**。因此三要素必须**分两层承担**：

| 层 | 承担者 | 适用规则 | 三要素如何实现 |
|---|---|---|---|
| **架构层** | `import-linter` / `pytest-archon` / 手写 pytest 架构测试 | 分层依赖、禁裸调用、禁字段注入 | **完全可自定义**：断言失败时输出完整三要素消息 |
| **风格层** | Ruff / mypy | 行长、命名、异常处理、类型 | 规则**代码** + 仓库内 `docs/conventions/rule-codes.md` 映射表；AGENTS.md 写明"遇到 TRY/RUF/PL 类报错先查该表" |

```python
# tests/architecture/test_layers.py
from pytest_archon import archrule

def test_layers_do_not_reverse_depend():
    (
        archrule("layer_dependency")
        .match("app.routers.*")
        .should_not_import("app.repositories.*")
        .check("app")
    )

LAYER_MSG = (
    "❌ 层级依赖违规：app.routers 不得直接依赖 app.repositories。\n"
    "✅ FIX: 在 service 中编排数据访问，router 仅持有 service 引用。\n"
    "   例：\n"
    "     class UserService:\n"
    "         def __init__(self, repo: UserRepository) -> None:\n"
    "             self._repo = repo\n"
    "📖 See: docs/architecture/boundaries.md"
)

def test_router_must_not_touch_repository():
    import app.routers.users as mod
    src = open(mod.__file__, encoding="utf-8").read()
    assert "repositories" not in src, LAYER_MSG
```

**把主观品味翻译成机械规则** `[书 p34]`：

> **经验法则：如果一条规则在 Code Review 中被提过 3 次以上，就应该写成 Linter 规则。**

| 团队口头约定 | 机械化规则 | Python 实现 |
|---|---|---|
| "方法要短" | 单函数 ≤ 50 行 | Ruff `PLR0915` |
| "文件要短" | 单文件 ≤ 300 行 | CI 文件长度检查 |
| "日志要规范" | 禁止 `print` / 裸 `except` | Ruff `T20` / `E722` |
| "HTTP 调用要统一" | 禁止裸 `requests.get` | import-linter / 架构测试断言 |
| "Router 要纯" | router 不得直接调 repository | import-linter layers |
| "依赖要注入" | 禁止模块级单例直取 | 架构测试 / `B008` |
| "测试要充分" | 行覆盖率 ≥ 80% | `pytest-cov --cov-fail-under=80` |
| "锁定工具版本" | 运行时 + Linter 版本固定 | `requires-python` + pin |

```toml
# 覆盖率门槛
[tool.pytest.ini_options]
addopts = "--cov=app --cov-fail-under=80 --cov-report=term-missing"
```

### A.3 反压模型 `[书 p14]`

| 类型 | 内容 |
|---|---|
| **上游反压** | 确定性设置、一致的上下文分配、**现有代码模式引导模型走向首选实现** |
| **下游反压** | 测试、类型检查、Lint、构建、安全扫描器和自定义验证器**拒绝无效工作** |

> `[推]` **上游反压 = 上下文工程 + 约束工程的「告知」面；下游反压 = 约束工程 + G3 门禁的「验证」面。**
> 自动化层不是新东西，而是把前两者的拦截能力**接到自动循环上**。

### A.4 熵管理：技术债务像高息贷款 `[书 p9 p11 p35]`

> OpenAI 采用**持续小额偿还**策略——他们把方法称为**垃圾回收**。最初每周五花 20% 时间手动清理低质量生成物，后来自动化为后台任务——**清理吞吐量与代码生成吞吐量成正比扩展**。

**三件套**：

1. **后台清理 Agent**（定时任务，7 项检查清单 + 约束）
2. **文档园丁（Doc-gardening Agent）**：后台扫描文档与代码的不一致，发现过时内容自动提交 PR——**Agent 为 Agent 维护文档**
3. **增量偿还**：不做大重构，做小 PR

**可观测性接入** `[书 p11]`：**将可观测性连接到 Agent**——赋予它查询日志和指标的能力，"**将启动时间降至 800ms 以下**"就变成了**可度量的目标**。

**Agent 排错 Prompt 模板** `[书 p39]`：

```
应用在 /api/users 端点返回 500 错误。
请查看日志中最近 5 分钟的错误记录，对照 traceId 找到完整调用链，
定位根因并修复。修复后重新跑全量校验与对应的单元测试。
```

**上下文污染的缓解** `[书 p12]`：最小化控制台输出、**日志写入文件**、使用 **grep 友好的错误格式**（`ERROR: [reason]` 单行）、**预计算聚合统计而非输出原始数据**。

> → 给 Agent 看的日志必须**机器可 grep、可聚合**，否则**日志本身会成为新的上下文污染源**。

### A.5 持久化记忆与结构化执行 `[书 p8-9]`

> 核心原则：**进度持久化在文件系统上，而非上下文窗口中。**

**两阶段模型**：初始化 Agent（建 `init.sh` + `progress.txt` + 初始提交 + 结构化功能列表）→ 编码 Agent（增量进展 + 结构化更新）。

**会话启动五步**（编码 Agent 每次醒来第一件事）：

```
1. 运行 pwd 确认工作目录
2. 读取 git log 与 progress.txt，了解最近的工作
3. 读取 feature list，选择最高优先级的未完成功能
4. 启动开发服务器，运行基础端到端测试
5. 确认基本功能正常后，再开始新功能开发
```

> **关键发现：使用 JSON 追踪 feature 状态比 Markdown 更有效**——因为 Agent 不太可能不恰当地修改或覆盖结构化数据。

**结构化执行**：所有团队都施加了**理解 → 规划 → 执行 → 验证**的序列。

> **人工检查点的价值：审查计划远比审查代码快。当规格正确时，实现自然可靠；当规格有误时，可以在 500 行代码生成之前及时纠正。**

**时间盲区对策** `[书 p12]`：每个 Agent 运行**随机 1–10% 的测试**，但子采样对单个 Agent 是确定性的、跨 VM 是随机的——**所以集体覆盖了完整测试套件**。

**CI 作为 Harness** `[书 p12]`：接近尾声时模型频繁破坏现有功能，修复方案是**一个更严格的 CI 流水线**——**用 Harness 层面的解决方案应对模型层面的问题**。

## 贯穿机制 B：证据层 ★（Track D 独有）

### B.1 证据包（放行前置产物）`[K]`

> **没有证据包，不得申请放行。**

```
已运行命令（原样贴出，不转述）
├─ 单元测试：x/y
├─ 契约测试：x/y
├─ 端到端测试：x/y
└─ CI：状态 + 构建编号/链接

已验证的失败路径（逐条列出）
受控突变的捕获结果
diff 范围（含 staged/unstaged 判定）
未验证事项（逐条列出）
剩余风险与不可逆后果
```

**❌ 反面示例（禁止）**：

```
用户注册功能已经完成，可以进入下一阶段。
```

**✅ 正确示例**：

```
已运行：
  - 单元测试：12/12
  - 契约测试：4/4
  - 端到端测试：2/2
  - 失败路径：已验证 3 项
  - CI：通过，构建编号 xxx

未验证：邮件服务真实环境 / 并发注册 / 数据迁移回滚

结论：
  - 技术完成度：核心路径达标
  - 可放行范围：可进入隔离环境集成阶段
  - 禁止进入：生产发布阶段
```

> **阶段结论必须具体到"可以进入哪一个阶段"，不能使用笼统的"可以继续"。** 这就是 [D2 §2.3 双轴判定](/process/control-model) 在报告格式上的落地。

### B.2 验证的观察力证明（两处）

| 时点 | 证明什么 | 方法 |
|---|---|---|
| **配置期（S2/G2）** | 约束规则**真的生效** | 故意写违规代码，确认报错含三要素且 CI 拦下 |
| **切片期（S3/G3）** | 测试**真的有观察力** | 受控突变，确认被捕获 |

> 这两处是本流程**最容易自欺**的地方：**"检查跑通了"不等于"约束生效"；"测试通过"不等于"测试能失败"。**

### B.3 Gate Record（可审计记录）`[K]`

每次阶段结束后保存一份：

```markdown
# Gate Record

- 项目 / 阶段 / 审查时间
- 审查基点（fixed point）/ 规格版本 / 代码版本
- 审查者（独立上下文标识）/ 执行者

## 必须项
| 项目 | 状态 | 证据 | 是否阻塞 |

## 已运行命令
## 失败路径和边界
## 未验证事项
## 剩余风险
## 不可逆后果
## 允许进入
## 禁止进入

## 结论
- [ ] A 完全达标   - [ ] B 有条件达标   - [ ] C 未达标，不得放行

## 重新验证条件
```

**价值**：结论前后变化时能定位——**当时依据了什么证据 / 哪个问题被遗漏 / 是新事实出现还是早期判断错误 / 是否需要修正流程**。

## 贯穿机制 C：控制层 ★（Track D 独有）

### C.1 独立校验上下文 `[K]`

阶段执行完成后，**开启新的审查上下文**，提供：阶段目标 / 已批准规格 / 交付文件 / 测试输出 / CI 地址 / 变更 diff。

> **不要只让同一个上下文重新阅读自己的输出。**

### C.2 放行权与执行权分离 `[K]`

```
高风险项目：
AI 执行 → AI 形成证据包 → 独立审查者复核 → 人工决定放行

AI 可以建议「未达标」，
但不能自行把高风险工作标记为生产可发布。
```

### C.3 用户复盘五问（每次 AI 报告完成时）`[K]`

用户不需要理解每一行代码，但**不能再只做"同意/不同意"这一个动作**。至少检查五个问题：

```
1. 你声称完成的每一项，证据是什么？
2. 哪些验收标准没有实际运行验证？
3. 当前明确剩下哪些问题？
4. 这些问题为什么不阻塞下一阶段？
5. 如果判断错误，最坏不可逆后果是什么？
```

**可直接复制的追问话术**：

```
不要重复总结你做了什么。请只回答：

1. 你声称已完成的每一项对应什么实际证据？
2. 哪些事项只是推测、默认或静态阅读，尚未运行验证？
3. 当前所有未完成项和剩余风险是什么？
4. 哪些问题会阻塞下一阶段？为什么？
5. 哪些问题不能进入「后续再补」？
6. 如果现在放行，最可能在哪个环节失败？
7. 请重新给出三级结论，并逐项引用证据。
```

> **如果 AI 不能回答，就不要批准进入下一阶段。**

### C.4 阶段放行审查提示词的十条约束 `[K]`

```
你现在是第三方评审官，不是本阶段执行者。
先完成完整校验，再输出结论。禁止先给结论再补问题。
主动寻找失败理由，而不是为进入下一阶段寻找理由。

1. 没有明确证据证明完成的事项，一律按未完成处理
2. 推测、默认值和理论可行性不能算完成证据
3. 任何未验证的异常、边界、依赖、风险或交付物都必须列出
4. 如果发现一个阻塞项，不能输出「完全达标」
5. 不得隐瞒剩余问题
6. 不得把「可以后续处理」当作当前阶段通过理由
7. 阶段结论必须与校验结果逐项一致
8. 不得修改代码来掩盖校验失败
9. 输入信息或验收标准不足时，先指出缺失，不得猜测
10. 结论只能使用规定的三级结论之一
```

## 度量：怎么知道流程真的生效了

**你要测量的不是"AI 是否会输出更严谨的检查表"**，而是：

| 指标 | 含义 | 健康方向 |
|---|---|---|
| **假阳性率** | AI 首次阶段判定被独立复核推翻的比例 | 下降 |
| **遗漏提前发现率** | 哪些遗漏被新规则提前发现 | 上升 |
| **批准耗时** | 用户批准所需时间是否增加到不可接受 | 不显著上升 |
| **单切片修复轮次** | 从失败到全绿要几轮 | 下降 |
| **规则命中率** | Linter 拦下的问题中，多少是 Agent 自己修的 | 上升 |
| **人工介入频次** | 每切片需要人介入几次 | 下降（G1/G2/G4 必须保留） |
| **CI 失败率趋势** | 是否在上升 | 平稳/下降 |
| **文档新鲜度** | 超 60 天未更新的设计文档数 | 接近 0 |
| **重复违规** | 同一条规则被违反的次数 | 反复违反 → **规则本身有问题** |
| **上下文预算** | AGENTS.md 行数 | 见 A.1 诚实提示 |

> **重复违规是极强的信号**：元规则说"Agent 犯错 → 改环境"。某个错误反复出现，说明**上一轮环境改动没生效**——要么规则没绑进 CI，要么 FIX 信息不够具体。

### 机制成本账与移除条件 `[推]`

> 指标不能只是**记分牌**，必须是**决定机制生死的反馈闭环**。本节给每个机制接上它原本没有的两样东西：**成本档位** 与 **移除条件**。
> **没有"删规则"的节奏，流程只会膨胀；"可以跳过"不足以防膨胀。**

**成本档位**：S ≈ 半天内 · M ≈ 1–2 天 · L ≈ 3 天以上（含持续成本）

| 机制 | 搭建 | 每切片 | 移除条件（若该度量不变，就删掉它） |
|---|---|---|---|
| 活契约（≤100 行） | S | ≈0 | 「重复违规」不降 → 规则本身没用 |
| 工具链版本锁定 | S | 0 | 从未发生版本漂移 → 可放宽为文档声明 |
| Linter 三要素 | M（每条约 30min） | 0 | 某条规则 12 个月零命中 → 删该条 |
| 分层依赖检查 | M | 0 | 从未违规 → 降为文档声明 |
| 覆盖率门槛 ≥80% | S | 每切片 +10–20% 测试时间 | 覆盖率已 >90% 且缺陷率不降 → 门槛不再是瓶颈 |
| 受控突变（每切片 1 项） | S | 每切片 +15min | **若从未捕获过任何破坏 → 不是删它，是要加**（说明测试缺观察力） |
| 证据包 | S | 每切片 +10min | 假阳性率不降 → 说明证据没被真正阅读 |
| 独立校验上下文 | S | 每切片 +1 会话 | 两判一致率 100% 且零遗漏 → 可降频 |
| 双盲重审抽样 | S | 每 N 次 +1 会话 | 假阳性率 <5% → 降频 |
| Gate Record 全量存档 | S | 每门 +10min | 从未被回查 → 只存 A/B/C + 阻塞项 |
| 后台清理 Agent | **L** | 持续 API 成本 | **单人默认不开**；清理 PR 被驳回 >50% → 停 |
| 文档园丁 Agent | M | 周期 API 成本 | 同上 |
| 可观测性全栈 | **L** | 运维成本 | Agent 从不查日志 → 只留结构化日志落文件 |
| 每周环境审查 | 0 | 30min/周 | 连续 3 个月零发现 → 降为月度 |

> **规模提示**："垃圾回收吞吐与代码生成吞吐成正比扩展"是 **3 人 / 3.5 PR·人日** 规模下的策略。**对单人项目，周期性后台 Agent 的 API 支出 + 审查负担大概率负 ROI**——按 [D2 §2.8](/process/control-model) 默认关闭。

### 双盲重审抽样：让「假阳性率」真的可测 `[推]`

> 上表的"假阳性率"需要一个**分母**。只做一次判定，这个率无从计算——**你只是在测自己**。

**机制**：每 N 次放行判定（单人建议 N=5），让第二个**独立上下文**在**看不到第一次结论**的前提下重审同一份证据，然后比对：

```
两判一致   → 记 1 次分母，0 次假阳性
两判不一致 → 记 1 次分母，1 次假阳性；并复盘归因
```

**两种不一致必须分开归因**（否则修错东西）：

| 类型 | 含义 | 修什么 |
|---|---|---|
| **标准歧义** | 同一份证据两人读出不同结论 | 修**证据充分性阈值**的措辞 |
| **证据缺失** | 第二人发现第一人漏看的事实 | 修**证据包格式**，把该字段设为必填 |

> **测不出来的指标不要写进规范。**
