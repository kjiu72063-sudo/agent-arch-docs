| `maven-enforcer-plugin` | 锁定工具链版本 | `requires-python` + `ruff target-version` + pre-commit pin | **第零道防线** |
| `ArchUnit` | 分层依赖、禁裸调用、禁字段注入 | `import-linter` / `pytest-archon` / 手写架构测试 | **唯一能完全自定义三要素消息的一层** |
| `Checkstyle` | Linter + 自定义错误消息 | `Ruff` | Ruff **不支持自定义文本** → 需 `rule-codes.md` 映射表 |
| `SpotBugs` | 静态缺陷 | `ruff`（B/RUF）+ `mypy` | |
| `JaCoCo` ≥80% | 覆盖率门槛 | `pytest-cov --cov-fail-under=80` | |
| `mvn -B clean verify` | 统一验证入口 | `pytest` + `pre-commit run --all-files` | |
| Spring 分层 | 架构基线 | `schemas → config → repositories → services → routers` | |
| Actuator + Micrometer | 应用指标 | `structlog` / `prometheus-fastapi-instrumentator` | |
| Loki / Promtail / Grafana | 日志与可视化 | 同（docker compose） | **Agent 需能自己查日志** |
| Puppeteer MCP | 浏览器自动化验证 | Playwright | 端到端验证的关键 `[书 p13]` |
| JUnit 5 + Mockito | 单元测试 | `pytest` + `pytest-mock` | |
| 完整 mutation 平台 | 测试观察力 | `mutmut` / `cosmic-ray` | 受控突变是其**轻量替代** |

### 16.1 TypeScript 侧映射 `[推]`

| 职责 | TS 等价 | 三要素如何实现 |
|---|---|---|
| 分层依赖 / 依赖方向 | **`dependency-cruiser`** | 规则可带 `comment` 字段承载 ❌/✅/📖 文案 |
| 架构 / 接口约束 | `eslint`（含 `@typescript-eslint`）自定义规则 | **ESLint 支持自定义 message**，可完整承载三要素 |
| 风格约束 | `eslint` + `prettier` + `stylelint` | 规则码 + `docs/conventions/rule-codes.md` 映射表 |
| 类型检查 | `tsc --noEmit` | 报错自带位置；补指引需文档 |
| 覆盖率门槛 | `vitest --coverage` + thresholds | 门槛配置化 |
| 单文件 / 单函数长度 | `eslint max-lines` / `max-lines-per-function` | 消息可自定义 |
| 受控突变 | `stryker` | 轻量替代：手工破坏 1 处关键逻辑，确认被捕获 |
| 统一验证入口 | `scripts/verify.sh` | 前后端共用同一入口 |

> **一个重要的公平修正**：TS 生态在"**自定义错误消息**"上**比 Python 更宽裕**——`dependency-cruiser` 有 `comment`、ESLint 有 `message`，三要素在 TS 侧能**接近完整实现**；而 Python 侧因 **Ruff 不支持自定义文本**，风格层只能退化为规则码映射表。
> 换言之：**以 Python 为首要示例，是因为栈的选择，不是因为 Python 更适配。**

### 16.2 Agent 工具选型 `[书 p40-41]`

| 场景 | 推荐 | 理由 |
|---|---|---|
| 个人项目，快速体验 | **Aider** | 30 分钟上手；Repo Map 天然实现"渐进式披露"；可配测试命令作为自动反馈回路 |
| 团队项目，需要流程控制 | **Cline + Superpowers** | Plan/Act 模式让你审批计划再执行；Superpowers 强制 TDD |
| 生产级，需要完全隔离 | **OpenHands** | Docker 沙箱确保 Agent 操作不影响主环境；模型无关 |

> **Superpowers 是目前 Harness Engineering 思想最完整的开源实现** `[书 p40]`，核心流程：
> `Brainstorming`（苏格拉底式追问）→ `Git Worktree`（隔离分支）→ `Writing Plans`（拆成 2–5 分钟微任务）→ `Subagent-Driven Development`（子 Agent 并行）→ **`TDD`（强制！RED→GREEN→REFACTOR）** → `Code Review` → `Finishing Branch`
>
> **杀手特性**：如果检测到 Agent 在测试之前写了实现代码，**直接删除那段代码，强制从测试开始**。

### 17.1 落地顺序：2 条保护机制 + 1 台测量仪 `[推]` ★

> 上表是**目标清单**，本节是**启用顺序**。**两者不是一回事——清单可以很长，启用必须最短。**
> 这是对"瓶颈在基础设施"与"不要一步到位"的执行。

| 类别 | 启用项 | 它治什么 | 为什么排第一 |
|---|---|---|---|
| **保护 a** | **G3 放行 = 证据先于结论 + 三级 verdict** | 根因：执行者自审 → 乐观完成 → 被打脸 | 直击根因，且**零工具成本** |
| **保护 b** | **每重要切片至少一项受控突变** | "测试全绿但无观察力"——最隐蔽的一类假绿 | **零依赖、15 分钟** |
| **测量仪 c** | **双盲重审抽样（单人 N=5）** | **不治任何问题，只产生数据**——给"是否该进第二版"提供分母 | 成本低；**缺它则 v1 无法证明自己** |

> **为什么测量仪必须进第一版**：曾有一版把双盲抽样排进"第一版不启用"，同时又用"假阳性率下降"作为进入第二版的条件——**这是一个闭环断口：v1 里没有工具能测出升版所需的那个数。**
> 测量仪与保护机制不同类：**它不增加门禁、不增加阻塞**，只多花"每 5 次判定 1 个会话"。

**第一版明确不启用**（全部延后，不是放弃）：

```
Linter 三要素体系 / 分层依赖断言 / 覆盖率门槛 / Gate Record 全量存档 /
六角色分工 / 后台清理 Agent / 文档园丁 / 可观测性全栈 / L3 全套门禁 /
每周环境审查
```

**进入第二版的判据（v1 内可测）**：

```
① 分母齐备：至少产生 N 次双盲比对记录（单人默认 N=5）—— 无数据即不进 v2
② 观察到 ≤1 次假阳性：说明 a + b 已见效
③ 每一条不一致都已归因（标准歧义 / 证据缺失）

三条同时满足 ⇒ 启用下一条机制
任一条不满足 ⇒ 不启用，先修 a / b / c 自身
```

**禁止事项**：

```
禁止一次性铺开
禁止因为「清单上还有没做完的」就阻塞发布（生产级不是文档数量）
禁止在缺 ① 分母时凭「感觉变好了」进入第二版 —— 这本身就是一次假阳性
```

> **本节是整份流程元规则在流程层的应用**：Agent 每次失败都是环境设计不完善的信号 → 同理，**流程每次新增机制都应是对一个真实失败的回答，而不是对流程完整性的想象。**

## 18. 反模式与踩坑 `[书 p46-48]`

| # | 症状 | 原因 | 解法 |
|---|---|---|---|
| 1 | **AGENTS.md 写太长** → Agent 输出质量反而下降 | 上下文窗口被指令文件占满 | 压缩到"地图 + 硬性规则"两类；**导航表、踩坑索引、目录结构不算"太长"**。⚠️「≤100 行」**在实际仓库被证伪**——降级为提醒。真正判据是：**有没有挤掉"正事"** |
| 2 | **Linter 规则太多 → Agent 陷入死循环** | 规则互相冲突 / 修复信息不足 | ① **逐条添加**，每加一条让 Agent 试跑 ② 每条 FIX 给**具体代码片段** ③ 冲突规则**只保留一条** |
| 3 | **工具链版本漂移** → 升级后构建抛不兼容错误 | 工具最新版已不支持旧运行时 | ① 显式锁定兼容版本 ② 依赖升级配置 `ignore` 阻止误升级 |
| 4 | **架构约束太严，阻碍合理跨层调用** → 团队开始绕过规则 | 规则未留豁免通道 | 设**豁免白名单**（如 `..legacy..` 排除），而不是删规则 |
| 5 | **文档园丁没人管 → 文档比不写还误导** | 缺自动化，文档单向腐烂 | ① 加**文档新鲜度检查** ② 每两周跑文档园丁 ③ 文档加 `status`，过期标 `deprecated` |
| 6 | **过度依赖 Agent，忘了「审查环境」** | 注意力全在产出，不在护栏 | 每周 30 分钟**环境审查**四问 |
| 7 | **AI 自检自判自放行** → 过度乐观 | 执行/验收/放行同一上下文 | ① 证据包前置 ② 独立校验上下文 ③ 双轴判定 + 三级结论 ④ 放行权分离 |
| 8 | **「测试通过」被当作质量证明** | 测试可能没有观察力 | 受控突变 + 配置期故意违规验证 |
| 9 | **用模糊表述替代证据** | "应该没问题""后续可以补" | 未证明即未完成硬规则；模糊表述只能进"推测" |
| 10 | **「有条件达标」变成新的乐观出口** | 定义太松 | 收紧定义 + B 的防滥用三件套 + 明确"不得归入 B"清单 |

**每周环境审查四问** `[书 p48]`：

```
最近一周的 CI 失败率是否上升？
规则是否覆盖了新出现的 bad pattern？
AGENTS.md 与 docs/ 是否跟代码库一致？
是否有人在尝试升级到不兼容的版本？
```

**跳过流程的判据** `[K]`——出现以下情况**可以跳过**某机制（但必须记录理由）：

```
它不能降低当前风险          它只是重复已有结论
它只增加文档或 tracker 维护成本
项目规模不足以产生协作收益    该阶段没有明确要验证的问题
```

> 跳过必须记录理由，但**不需要为了"流程完整"补做无价值文档**。

## 19. 持续维护节奏

### 20.2 验证台账：15 条关键规则的实际验证状态 ★

> **这是全章最诚实、也最有价值的一节。** 它证明：**`[书]` 标记只能证明"来源可查"，不能证明"结论正确"。**

| `[书]` 规则 | 出处 | 状态 | 证据 / 备注 |
|---|---|---|---|
| 分层依赖必须**机械化强制** | `[书 p9 p11]` | ✅ **已验证** | 实际仓库 `verify.sh` 含分层依赖闸（2 kept / 0 broken）+ 前端 `dependency-cruiser`（48 模块零违规） |
| 覆盖率 ≥80% 门槛 | `[书 p26-29]` | ✅ **已验证** | 后端实测覆盖率 96.34%–96.65%，门槛长期通过 |
| 单文件 ≤300 行 / 单函数 ≤50 行 | `[书 p31]` | ✅ **已验证** | `verify.sh` 文件大小闸 + 前端 lint 强制 |
| 工具链版本必须锁定（第零道防线） | `[书 p50]` | ✅ **已验证** | `pyproject.toml` + `uv.lock` + `package.json` 与技术栈基线交叉校验 |
| 两阶段模型 + 会话启动五步 + **JSON > Markdown** | `[书 p8 p12]` | ✅ **已验证** | 启动脚本实现五步；`feature_list.json` 长期用 JSON，未发生误改 |
| 「约束必须在 CI 物理拦截」 | `[书 p15]` | ✅ **已验证** | CI 质量门 5 job + 与本地 14 闸门映射 |

### 20.3 收口：三句话

> `[书 p49]` Harness Engineering 的核心**不是搭建复杂的基础设施**，而是一个简单的闭环——**约束 → 告知 → 验证 → 纠正**。**从 AGENTS.md 和一条规则开始，比什么都不做强一百倍。**

> `[书 p50]` Birgitta Böckeler：**为了获得更高的 AI 自主性，运行时必须受到更严格的约束。增加信任需要的不是更多自由，而是更多限制。** 就像高速公路上的护栏——**正是因为有护栏，你才敢踩到 120 码。**

> `[书 p51]` 软件开发的未来，可能不再是关于我们能写多快多好的代码，而是关于我们**能设计多聪明、多鲁棒的系统来驾驭 AI 代理的巨大能量**。工程师的价值正在从执行者转变为赋能者和系统思考者——**从构建产品转向构建能够构建产品的工厂。**

**最后一条，也是最重要的一条** `[K]`：

> **AI 没有证明「可以放行」，就只能判定为「不能放行」。**
> 用户不需要理解全部代码，但必须看到**证据、未验证项、阻塞项和最坏后果**。
>
> 这能显著降低"先乐观放行、后被迫补问题"的矛盾，但**不能保证 AI 永不犯错**。真正可靠的标准不是"AI 永远正确"，而是：
>
> **错误判断必须在进入不可逆阶段之前，被独立证据和复核拦住。**
