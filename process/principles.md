# D1 · 第一性原理：从教材到流程

> **理论锚点**：[03 harness](/concepts/harness)（同一教材 S11）——本节把教材的"机制"翻译成"流程律"。

## 1.1 定义、哲学与唯一元规则 `[书 p3]`

> Harness Engineering 是围绕 AI 智能体设计和构建**约束机制、反馈回路、工作流控制和持续改进循环**的系统工程实践。它**不优化模型本身，而是优化模型运行的环境**。核心哲学八个字：**人类掌舵，智能体执行**。

教材引 Mitchell Hashimoto 原话：

> anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent will not make that mistake again in the future.

**元规则（本流程的地基）**：

> **Agent 每一次失败，都是环境设计不完善的信号。** 正确回应不是换个更强的模型，而是**重新设计它运行的环境**。

→ **操作化**：每次 Agent 出错，**禁止只做"手动修掉"**，必须回答：

```
这次要不要新增一条规则 / 一个测试 / 一条文档，让它永不再犯？
```

> 这条元规则贯穿全流程：S5 复盘的退出证据里明确要求"本轮新规则中，哪些是『失败 → 改环境』的产物"。

## 1.2 Harness 在哪一层 `[书 p5]`

Harness **不是** SDK、脚手架或 Agent 框架的替代品，而是**位于它们之上的一层**：

> 模型正在吸收框架约 **80%** 的功能（智能体定义、消息路由、任务生命周期……），但剩余 **20%**——**持久化、确定性重放、成本控制、可观测性、错误恢复**——正是驾驭层存在的价值。

→ **设计律**：别重复造框架已有的轮子。**精力全投在那 20%。**

## 1.3 三次跃迁 `[书 p5]`

| 范式 | 核心问题 | 优化对象 | 交互模式 | 本站 |
|---|---|---|---|---|
| 提示词工程 | 怎么把话说清楚 | Prompt 的措辞、格式、示例 | 一问一答 | [Track A · 01](/concepts/prompt) |
| 上下文工程 | 怎么给 AI 喂信息 | 文档、代码片段、历史对话 | 信息注入 → 生成 | [Track A · 02](/concepts/context) |
| **驾驭工程** | **怎么让 Agent 可靠工作** | **约束、反馈回路、控制系统** | **人类掌舵，Agent 执行** | [Track A · 03](/concepts/harness) + **本 Track** |

教材类比：提示词工程是"**对马喊话的技巧**"，上下文工程是"**给马看的地图**"，**驾驭工程是"给马造一条高速公路，配上护栏、限速牌和加油站"**。

## 1.4 四类失败模式 → 四道防线 `[书 p6]`

**这是本流程所有门禁的由来**——每一个门禁都在防下面某一类失败：

| 失败模式 | 症状 | 本流程的防线 |
|---|---|---|
| ① **试图一步到位** | 一个会话干完所有功能 → 上下文耗尽，留下无文档半成品 | **S3 纵向切片**（一个切片一个会话） |
| ② **过早宣布胜利** | 看到有进展就宣布完成，大量功能未实现 | **G4 发布闸**（端到端，非单元测试） |
| ③ **过早标记功能完成** | 写完代码就标 done，没做端到端测试 | **G3 切片闸** + 证据包（[D6](/process/mechanisms)） |
| ④ **模式复制** | 库里有什么模式就忠实复制并放大——**包括坏模式和架构漂移** | **约束工程**（最危险的一条，见 [D6](/process/mechanisms)） |

> 注意 ④：前三类是"做不完/做不实"，第四类是"**做得又快又歪**"。它解释了为什么"约束必须自动化"——**Agent 的复制能力既是优势也是风险放大器**。

## 1.5 六条共识 → 六条流程设计律 `[书 p14-15]`

业界六个独立来源形成的共识，右侧是**本流程对它的操作化**：

| # | 共识 `[书]` | 转成流程设计律 `[推]` |
|---|---|---|
| 1 | 瓶颈在基础设施，不在模型智能 | 效果差时**先查环境再换模型** |
| 2 | 文档必须是活的反馈循环 | 文档与代码**同一 PR** 更新；**过期文档视为缺陷** |
| 3 | 思考与执行分离 | 规划与实现**不同会话 / 不同 Agent**，状态存外部 |
| 4 | 上下文不是越多越好 | Tier1 ≤ 100 行；其余**按需检索** |
| 5 | 约束必须自动化 | **上过 Code Review 3 次的规则 → 必须写成 Linter** |
| 6 | 工程师角色在转变 | **你的产出是"环境"，不是代码** |

::: tip 共识 5 是最具操作性的那条
"提过 3 次以上就写成规则"给出了一条**可执行的阈值**——它把"要不要自动化"从判断题变成了计数题。
:::

## 1.6 核心闭环 `[书 p49]`

```
约束  →  告知  →  验证  →  纠正
 ↑                            │
 └──────────  回写环境  ───────┘
```

| 环节 | 做什么 | 在本流程里 |
|---|---|---|
| **约束** | 把纪律写成机器能执行的形式 | S2 设计（[D4](/process/stages-1)） |
| **告知** | 让 Agent 知道规则与边界 | 上下文工程（[D6](/process/mechanisms)） |
| **验证** | 机械化判定是否达标 | G3 切片闸 + 证据包（[D5](/process/stages-2)） |
| **纠正** | 失败信息回灌 + 回写环境 | 元规则（§1.1）+ S5 复盘 |

> 核心**不是搭建复杂的基础设施**，而是一个简单的闭环。**从 `AGENTS.md` 和一条架构规则开始，比什么都不做强一百倍。**

|---|---|

| 什么情况下必须把口头约定写成 Linter？ | 共识 5：Code Review 提过 3 次以上 |
| 本流程的四个环节是什么？ | 约束 → 告知 → 验证 → 纠正 |
