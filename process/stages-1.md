# D4 · 阶段细则（上）：S0 基线 / S1 定义 / S2 设计

> **理论锚点**：S0–S2 是 [03 harness 落地三步走](/concepts/harness/design) 的"信息层 → 约束层"在项目生命周期里的展开。

---

## S0 基线 —— 让项目可被 Agent 安全运行

### 目标

把一个裸仓库变成"**Agent 可以放心动手**"的环境。

### 必须交付物

- 可回滚的基线提交
- 语言 / 运行时 / 包管理器 / 测试命令 / 部署环境的**记录**
- 最小本地检查 + CI 入口
- 敏感文件、环境变量、生成物的排除规则

### 必须完成

> ⚠️ 本表的**强制力依据验证台账**，不依据教材语气（规则见 [D0 标记法](/process/)）。
> 标 `✅` 者为硬性规则；标 `⏳` 者按默认规则属"教材意见"，**只能作建议**。

| # | 动作 | 教材对应 | 验证状态 → 强制力 |
|---|---|---|---|
| 1 | **锁定工具链版本** | `[书 p50]`"这不是可选项，是第零道防线" | ✅ 已验证 → **必须** |
| 2 | 建目录骨架 | `[书 p19]` `docs/{architecture,conventions,design,plans,reference}` | ✅ 已验证（实际仓库另扩 `handbook/` `operations/`）→ **必须** |
| 3 | 建进度三件套 | `[书 p8 p12]` `init.sh` + `progress.txt` + `feature_list.json` | ✅ 已验证 → **必须** |
| 4 | 建隔离机制 | `[书 p36 p14]` Git Worktree 或容器沙箱 | ⏳ **未验证** → **建议**（实际仓库未用 worktree，隔离由 Docker 沙箱承担——**同类需求，不同实现**。故本条要求是"**要隔离**"而非"**要用 worktree**"） |
| 5 | 声明唯一事实源 | `[书 p11]` 所有知识进仓库 | ⏳ **未验证（属原则，不可机械检查）** → **建议**；但后果明确：**写在仓库外的知识，对 Agent 等于不存在** |

### 退出证据

```
有可回滚基线（commit hash 可查）
团队知道如何运行最小检查（命令可复制执行）
未把本机路径、凭证或临时产物写入正式配置
隔离机制已验证可用
```

### 阻塞条件

```
无 Git 仓库 / 无回滚点
工具链版本未锁定 → 随时可能漂移
仓库外存在关键知识（对 Agent 等于不存在）
本地检查无法在干净环境复现
```

### Python 示例 `[推]`

```toml
# pyproject.toml
[project]
requires-python = ">=3.11,<3.13"     # 显式锁定，禁止漂移
dependencies = []

[tool.ruff]
target-version = "py311"
line-length = 100
```

```yaml
# .pre-commit-config.yaml —— 本地第一道闸，与 CI 同一套检查
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
```

> 关键：**本地闸与 CI 用同一套检查**。两者不一致时，本地过而 CI 挂——这会训练 Agent"本地通过就没事"的错误直觉。

### 工具使用边界 `[K]`

```
可自动：装 pre-commit、建 workflow、写配置文件
需确认：安装额外依赖、git add 全部文件、commit、推送
禁止：未经确认改远程、动凭证、绕过 hook（--no-verify）
```

## S1 定义 —— 先定目的，再谈实现

### 目标

让"**为什么做 / 做到什么程度 / 不做什么**"在写任何代码前收敛。

### 必须产出

```
一句话系统目的
目标用户和核心场景
可观察成功判据
当前版本做什么 / 明确不做什么 / 不承诺什么
已验证事实 / 待验证假设 / 未知问题   ← §2.2 五分类落地
风险等级及升级理由
核心输入到输出管道
最小可观察闭环
```

### 必须回答 `[K]`

```
这个系统为谁解决什么问题？
失败时影响什么？
如何知道它真的有效？
当前版本明确拒绝哪些范围？
```

### 退出证据（G1 目的闸）

```
目的是否能用一句话说明？
成功判据是否可观察（不是「性能好」而是「P95 < 200ms」）？
「非目标」栏是否明确写出？
风险等级及升级理由是否已记录？
```

### 阻塞条件

```
目的无法用一句话说明
成功判据无法观察
关键业务规则需要 AI 猜测
风险等级未定 → 无法决定启用哪些门
```

→ 输出：`暂不进入实现：目的或验收边界未收敛。`

> **不得让实现阶段自行补猜产品目标。**

### 业务假设验证（L1 以上）

必须区分：

```
用户需求证据 / 利益相关者要求 / 技术可行性 / 法律合规约束 / 仅由团队推测的愿望
```

可用方式：用户访谈、低成本原型、可控实验、真实数据形状检查、竞品分析、业务负责人确认。

> 原型可以验证"**用户是否需要**"和"**设计是否可用**"，**不能被当作生产质量证明**。

### 风险分级落点

按 [D2 §2.1](/process/control-model) 定级，输出：

```
项目等级 = L?
判定依据（风险最高项）= ?
触发的升级条件 = ?
该等级最低要求 = ?
```

## S2 设计 —— 把架构变成可执行的约束

### 目标

把"设计意图"转成**可机械化执行的约束**与**可冻结的规格**。

### S2.1 领域与架构（复杂时启用）

**领域复杂时**（多个领域名词、状态机、不变量、所有权、权限、事件/订单/支付/库存规则）→ 产出 `CONTEXT.md` / 领域文档 / ADR。

> ⚠️ **不得把术语文档写成未经批准的实现规范。**

**模块边界复杂时** → 重点分析：模块职责、输入输出、public seam、依赖方向、端口/适配器、接口深度与宽度、循环依赖与共享可变状态、替换实现的成本。

**退出条件**：

```
关键名词含义不冲突
跨边界契约可读、可测试
业务模块不依赖其他模块的具体实现
关键失败出口、重试、补偿和副作用已显式表示
```

### S2.2 分层依赖：把架构变成断言 `[书 p9]`

教材层级模型：`Types → Config → Repo → Service → Runtime → UI`，**下层不能反向依赖上层**，违反即 CI 阻止合并。

**Python 等价** `[推]`：`schemas → config → repositories → services → routers`

| 规则 | 说明 |
|---|---|
| `schemas` | **不依赖任何业务包**（纯模型） |
| `config` | 仅依赖 schemas |
| `repositories` | 仅依赖 schemas、config |
| `services` | 仅依赖 schemas、config、repositories |
| `routers` | 仅依赖 schemas、config、services |
| **`routers` 禁止直接依赖 `repositories`** | 必须经 service |
| `infrastructure` | 横切关注点：HTTP client、日志、指标、安全 |

> 理论锚点：[3-2 ArchUnit 分层规则](/concepts/harness/design)（Java 版）；[D7 模板库](/process/templates) 有 Python/TS 版。

### S2.3 安全、隐私、数据与运营门禁 `[K]`

**L2 按风险选择；L3 必须执行并取得明确批准。**

**安全与隐私**至少检查：

```
身份认证 / 授权与最小权限 / 租户隔离 / 数据分类 / 加密 / secret 管理 /
输入校验 / 速率限制 / 重放与幂等 / 审计日志 / 数据保留删除导出 /
依赖与许可证与漏洞与 secret 扫描
```

> **不得把代码审查当作安全评审的替代品。**

**非功能需求**必须用**可验证指标**表达：P95/P99 延迟、吞吐与并发、可用性与 SLO、容量上限、成本上限、RPO/RTO、可维护性、可访问性、数据保留期。

**数据与契约演进**：

```
版本化 → 向后兼容 → expand → migrate → dual-read/dual-write（如需要）
      → switch → contract
```

必须写出：备份 / 恢复验证 / 迁移失败处理 / 回滚或补偿 / 旧版本兼容窗口 / 部分完成后的数据状态。

> **不得把"有一个回滚脚本"当作已经验证过的回滚能力。**

**可观测性与运行准备**至少定义：结构化日志、metrics、tracing、correlation ID、业务指标、SLO dashboard、告警阈值与路由、runbook、on-call、事故分级与沟通。

### S2.4 规格固化

规格必须包含 **17 项**：

```
背景目标 / 非目标 / 用户场景 / 已确认领域对象 / 状态机与不变量 / 数据流 /
模块契约 / 正常路径 / 错误行为 / 权限与安全 / 迁移与回滚 / 可观测性 /
测试策略 / 验收标准 / 非功能要求 / 未决问题 / 明确不包含的内容
```

**状态机**：

```
spec-draft → spec-approved → tickets-approved → ready-for-agent
```

> 不应在票据和关键决策尚未确认时过早标记 `ready-for-agent`。**不得补写未确认的业务规则。**

### 退出证据（G2 规格闸）

```
关键名词含义不冲突，跨边界契约可读可测试
规格 17 项齐备，且「非目标」与「明确不包含的内容」非空
规格状态 = spec-approved（已由人类批准）
风险等级对应的门禁已按等级执行完毕
每条硬性规则都能指出「由哪个工具在哪一步强制」
```

> 最后一条是 **G2 最容易漏、也最关键的一条**：**答不出"哪个工具在哪一步强制"的规则，不是硬性规则，是建议**——应移到 `docs/`。

### 阻塞条件

```
规格与实现冲突
关键异常路径未定义
依赖未就绪
安全/隐私门禁未按等级执行（L3）
迁移与回滚未定义（涉及数据时）
存在未分类的风险
```

## 本节的流程输出

| 阶段 | 一句话 |
|---|---|
| **S0** | 让项目**可被 Agent 安全运行**：版本锁定 + 目录骨架 + 进度三件套 + 隔离 |
| **S1** | 让**目的收敛**：一句话目的 + 可观察判据 + 非目标 + 风险等级 |
| **S2** | 把设计**变成约束**：分层断言 + 安全门禁 + 17 项规格 + 每条规则可指认强制点 |
