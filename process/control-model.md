# D2 · 控制模型（本流程最大的结构升级）

> **理论锚点**：本节**在 Track A 中无对应**——A 讲"机制是什么"，本节讲"**当 AI 同时扮演执行者、验收者和放行者时，怎么不让它自我批准**"。这是 Track D 的核心增量。

## 根因

> **当 AI 同时扮演执行者、验收者和放行者时，必然产生过度乐观判断。**
> 把提示词写得更严格不够——**必须改流程、证据、交互规则三层**。

下面 8 个小节就是这三层的具体设计。

## 2.1 风险分级：先判断风险，再选择流程 `[K]`

不要先问"要调用哪些工具"，先回答：

```
这次变更影响什么用户、数据和外部系统？
失败后能否撤销、补偿或回滚？
是否涉及资金、个人数据、权限、合规或安全控制？
是否需要多人、多会话或跨模块协作？
是否存在尚未验证的产品、领域或技术假设？
```

> **等级按「风险最高项」决定，不按项目名称决定。** 一个小功能如果涉及支付或生产权限，也必须按高等级处理。

| 等级 | 典型特征 | 最低要求 |
|---|---|---|
| **L0** | 文档、格式、明显的单点修改、无行为变化 | 相关检查；必要时直接实现 |
| **L1** | 低风险单功能、内部工具、简单 UI、可完全撤销 | 简短规格 → 测试 → CI → 审查 |
| **L2** | 多状态业务、持久化、多模块、外部依赖、权限或用户数据 | S1 目的闸 → S2 规格闸 → 纵向切片 → 分层测试 → staging |
| **L3** | 支付、敏感数据、多租户、核心权限、合规、不可逆迁移、高可用 | L2 全部 + 安全/隐私/非功能/迁移/回滚/发布/事故门禁 |

**升级触发条件**（出现任一即升级，**不得继续套用原等级**）：

```
真实资金或不可逆外部副作用
个人敏感数据、医疗或合规义务
生产权限、身份系统或租户隔离
数据迁移不能简单回滚
单次失败可能造成大范围业务影响
需要多团队并行或跨多个会话协作
性能、容量、可用性目标尚未验证
规格、领域术语或模块边界存在实质冲突
```

> 分级的价值：**让流程可裁剪**。一套流程套所有项目，必然要么过重（L0 走全套）要么过轻（L3 走简版）。

## 2.2 事实五分类

所有设计材料必须区分，**不得混淆**：

| 类别 | 定义 | 禁止 |
|---|---|---|
| **已验证事实** | 已有代码、运行结果、用户证据或明确约束证明的内容 | — |
| **已批准决策** | 负责人明确选择并记录的方案 | 不得伪装成"事实" |
| **待验证假设** | 尚未由用户、实验、测试或运行数据证明的推测 | **不得伪装成冻结规格** |
| **未知问题** | 当前无法判断、必须进一步调查的事项 | 不得静默略过 |
| **暂定约束** | 为推进而暂时采用、后续可能撤销的选择 | 必须标注**可撤销** |

> **关键**：`待验证假设` **不得出现在「已完成」栏**。这一条直接决定了后面"未证明即未完成"能否执行。

## 2.3 双轴判定：把两个结论拆开 `[K]`

> **这是本流程最容易被混淆、也最关键的一条。**

| 轴 | 回答的问题 |
|---|---|
| **技术完成度** | 当前实现是否满足技术验收标准？ |
| **阶段可放行性** | 当前是否满足进入下一个阶段的前置条件？ |

**两者可以不同**，例如：

```
技术实现：已完成
测试：通过
阶段放行：不允许进入生产发布
原因：未完成 staging 迁移演练和回滚验证
```

```
功能实现：部分完成
允许进入：下一轮隔离环境测试
禁止进入：生产发布
```

→ **所以永远不要问"这个阶段完成了吗？"**，而要问三个问题：

```
实现验收是否通过？
当前允许进入哪个阶段？
当前禁止进入哪些阶段？
```

> 现实意义：**"完成了但不能发布"是最常见的真实状态**。二元门禁（通过/不通过）无法表达它，于是人们要么强行判"通过"（乐观放行），要么判"不通过"（阻塞合理进展）。

## 2.4 三级结论（定义已收紧） `[K]`

每个门禁**只能输出以下三者之一**：

### A. 完全达标

仅当**同时**满足：

```
所有必须项均有证据
+ 没有阻塞项
+ 下一阶段前置条件全部满足
+ 未验证风险不会改变当前结论
```

### B. 有条件达标

> 不是"还有问题但可以继续"，而是：只有剩余问题**已被隔离**、**不影响下一阶段目标**，并且有**明确责任人、硬性到期日、验证方式**时，才允许。

必须附：非阻塞问题 / 责任人 / 处理期限 / 不处理的后果 / 为什么不阻塞下一阶段。

**B 的防滥用三件套（缺一即降级为 C）：**

```
① 硬性到期日 —— 不是「尽快」，是可判定的日期或切片编号

② 到期自动降级 —— 到期未消除 ⇒ 变为 C，不需要任何人重新判定
   执行者（必须指名，否则「自动」是空话）：
     · 首选：verify.sh 或等价 CI 定时任务，复读 Gate Record 的 expires_at 字段，
             到期未消 ⇒ 自动把该记录判定改写为 C 并通知 owner
     · 退路：无调度器时，由每周环境审查人工复读
   ⚠️ 退路状态下本项必须标注「策略自动 / 实现人工」，不得声称已自动化

③ Gate Record 留痕 —— 记「谁读了证据、得出什么判断」，不记「通过」
```

> `[推]`"自动"**只有在调度器真实存在时才算自动**。只写政策不写执行者，是把一个判断换成了另一个判断——而判断正是失败源。
>
> B 的三条件（已隔离 / 不影响下一阶段 / 有责任人）本质仍是**判断**。三件套不消除判断，而是给判断装上**到期自动失效的开关**：一旦乐观判断错了，**纠错成本有限且可回收**，而不是无限延展。**没有 ②，B 就是新的乐观出口。**

**以下问题一律不得归入 B，必须是 C：**

```
主路径之外的关键失败路径未测
依赖尚未就绪
数据迁移未演练
权限边界未验证
构建或 CI 未通过
规格与代码不一致
任何不可逆副作用未确认
```

### C. 未达标，不得放行

只要存在任一阻塞项、关键事项无法确认、异常路径未验证、依赖未就绪、规格冲突或证据不足。

禁止只说"还有一些问题，建议后续完善"。**必须输出完整链条**：

```
阻塞项 → 事实证据 → 最小补救动作 → 重新验证命令 → 重新放行条件
```

> **禁止输出第四种结论。**

## 2.5 硬规则：未明确证明即未完成 `[K]`

> **没有明确证据证明完成的事项，一律按未完成处理。**

适用范围：

```
没有测试结果的功能      没有演练记录的回滚
没有运行输出的 CI       没有明确责任人的人工配置
没有实际验证的外部依赖   没有覆盖的异常路径
没有审查记录的安全要求
```

**以下表述只能放进「推测」或「未验证风险」，绝不能放进「已完成」：**

```
应该没问题 / 理论上可以 / 后续可以补 / 一般不会发生
代码看起来正确 / 测试应该覆盖了 / 生产环境再验证
```

## 2.6 控制权分离：执行 / 校验 / 放行 `[K]`

```
坏模式：AI 执行 → AI 自检（同一上下文）→ AI 宣布通过 → 用户盲批准

好模式：AI 执行
        → AI 产出证据包
        → 独立上下文（fresh eyes）复核
        → 判定技术完成度
        → 判定阶段可放行范围
        → 记录阻塞项与剩余风险
        → 人工批准或退回
```

**三条不可合并的原则：**

1. **自校验与执行不得共享同一上下文**——同源上下文会让 AI 为自己的实现寻找合理解释，而不是重新质疑前提；
2. **证据必须先于结论**——先完成校验并输出证据，再给结论；**禁止先给结论再补问题**；
3. **放行权与执行权分离**——AI 可以建议"未达标"，但**不能自行把高风险工作标记为生产可发布**。

> `[书 p9]` 教材对应机制：**智能体审智能体**（Agent-to-Agent Review）。`[推]` 审查者必须是**独立会话 / 独立上下文**——"写代码的 Agent 顺便审自己"会把作者偏见一并带进来。
>
> 理论锚点：[3-1 组件⑥ 反馈循环](/concepts/harness/mechanism)。

## 2.7 证据充分性阈值与停止规则 `[推]`

> **这是本流程对自身最严重漏洞的修复。**

§2.5"未证明即未完成"若不配停止规则，**字面上不可执行**：保险级的证明不存在，于是只有两条路——
① 所有阶段永远停在 C（**流程死锁**）；
② 人们非正式地自行"觉得够了吧"（**把乐观悄悄放回原位，正是要消灭的失败模式**）。

> 一个**没有终端判据**的"必须完全证明"，只会逼人恢复乐观或永不出货。

**修复方式**：把"未证明"从**无限回归**，改为**按等级预设的有限清单**——**清单内必须证明，清单外一律转为下一阶段任务。**

### 各等级的「证据充分」阈值

| 等级 | 判 A/B 所需的证据（**固定枚举，评审中不得追加**） |
|---|---|
| **L0** | 相关检查通过（lint / 类型）+ 影响面已声明 + 无未声明的文件改动 |
| **L1** | 一页规格 + **该切片的验收标准逐条有运行输出** + CI 在干净环境通过 |
| **L2** | L1 全部 + **至少 1 个失败/异常路径已验证** + **至少 1 项受控突变被捕获** + 双轴审查完成 + 迁移（如有）已在隔离环境演练 |
| **L3** | L2 全部 + 安全/隐私清单**逐项有结论**（通过或明确豁免 + 责任人）+ 非功能指标**有实测值** + 备份恢复演练有输出 + 回滚演练有输出 + 发布负责人与回滚触发条件已指名 |

**不足即 C 的情形**：上表任一项缺，或命中 §2.4 的"不得归入 B"七条。**除此之外不得判 C。**

### 停止规则（五条，硬性）

```
1. 每道门的证据清单是固定枚举 —— 评审中不得临时追加证明要求
2. 清单项全部有证据 ⇒ 停止收集，给出 A 或 B
3. 任何「还想再确认一下」的怀疑 ⇒ 写成下一阶段的切片任务或 backlog 条目
   （带风险等级），不阻塞当前门
4. 禁止用「更彻底地证明」作为推迟放行的理由
5. 若清单本身被证明不足（真实遗漏）⇒ 修清单本身并记入修订记录
   —— 这是元规则的应用：错的是环境，不是这一次判断
```

> **§2.5 与 §2.7 的分工**：§2.5 管"**什么不算证明**"，§2.7 管"**证明到哪就停**"。
> **缺前者纵容乐观，缺后者直接死锁。**
>
> 第 3 条是关键：它把"未验证的担忧"从**门的阻塞项**转化为**下一阶段的任务**——**无限回归被切断，但担忧不丢失**。

## 2.8 规模分级：机制启用矩阵 `[推]`

> 教材的多数实践来自 **3–5 人 / 16 Agent 规模**的团队。把它们的仪式照搬到单人项目，会把真实工作变成**流程表演**。下表按规模裁剪。

| 机制 | 单人 | 小团队（2–5） | 团队（>5） |
|---|---|---|---|
| 活契约（≤100 行） | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| Linter 三要素 | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| 工具链版本锁定 | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| 三级结论 + 证据包 | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| 受控突变（每切片 1 项） | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| 独立校验上下文 | ✅ 每次放行 1 次（新会话即可） | ✅ 必须 | ✅ 必须 |
| 双盲重审抽样 | ⚠️ 每周 1 次 | ✅ | ✅ |
| Gate Record | ⚠️ 只存 A/B/C 判定 + 阻塞项 | ✅ | ✅ |
| 六角色 Agent 分工 | ❌ 降为 3 角色（执行/校验/清理） | ⚠️ 按需 | ✅ |
| 后台清理 Agent | ❌ 改为每周手动收尾 30 分钟 | ⚠️ 月度 | ✅ 周期化 |
| 文档园丁 Agent | ❌ 每周手动一次 | ⚠️ 每两周 | ✅ |
| 可观测性全栈 | ⚠️ 结构化日志落文件即可 | ✅ | ✅ 全栈 |
| L3 全套门禁 | ❌ 见下 | ✅ | ✅ |

**单人项目的 L3 硬约束** `[推]`：单人若命中 L3 特征（真实资金 / 敏感数据 / 权限 / 不可逆迁移），**必须先解决"无第二人复核"这一结构性风险**（外部复核人或托管服务），否则**不得发布**。

> **加再多门禁也替代不了第二个人的判断。**

**meta 层同构约束** `[推]`：既然本流程禁止"同源自审"，**它的复核体系本身也不得只有单一维护者**。
单一维护者不能只是一个被命名的风险——必须在 G5 复盘中**实际执行一次外部盲审**：把一份 Gate Record 的证据包交给**未看过第一次结论**的第二个上下文或第二个人重审。**不等 L3、不等"有人可用"。命名风险不等于处理风险。**

## 本节的流程输出

| 你在什么场景 | 用哪几条 |
|---|---|
| 拿到一个需求，先做什么 | §2.1 定级（不是先想工具） |
| 文档里怎么写现状 | §2.2 五分类（假设不得进"已完成"） |
| 评审时怎么给结论 | §2.3 双轴 + §2.4 三级 |
| 有人问"证明到什么程度" | §2.7 阈值 + 停止规则 |
| 判断要不要上某机制 | §2.8 规模矩阵 + [D8 成本账](/process/tooling) |
